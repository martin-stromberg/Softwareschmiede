# Bestandsaufnahme: Abschlussüberwachung — terminal ungeklärtes Ereignis blockiert Auto-Completion dauerhaft (Issue #441)

Bestandsaufnahme des bestehenden Codes für die Anforderung, das Gate der Abschlussprüfung (`ScmTaskCompletionMonitoringService.CheckTaskAsync`) gegenüber terminal ungeklärten Ereignissen zu differenzieren und die Registrierung einer im Abschluss gemeldeten `pullRequestNumber` vom sauberen Abschlusspfad zu entkoppeln.

## Zusammenfassung

- **Das blockierende Gate existiert an zwei Stellen**: `ScmTaskCompletionMonitoringService.CheckTaskAsync` bricht vor der Referenzprüfung ab, sobald irgendein `ScmIncomingEvent` der Aufgabe einen anderen Status als `"Verarbeitet"`/`"Abgebrochen"` trägt (Zeilen 84–86); dieselbe Prüfung wird innerhalb der `ScmTaskCoordinator.Shared.RunAsync`-Sperre vor dem eigentlichen Abschluss wiederholt (Zeilen 133–135). `VerarbeitungUngeklärt` blockiert damit beide Prüfungen permanent — es gibt keinen automatischen Übergang aus diesem Status.
- **`ScmIncomingEvent.Status` ist ein freies String-Feld** (Default `"Aufgenommen"`); zehn Statuswerte kommen im Code vor, verteilt auf `ScmEventOrchestrator` (Setzen), `ScmEventStore` (`"Verzögert"`), `ScmTaskCompletionMonitoringService`, `ScmEventExchangeService`, `ScmDispatchPriority`, `RunningAutomationsCount`, `MainWindowViewModel` und `ScmEventQueueViewModel` (Lesen/Filter). Es gibt **keine zentrale Status-Konstanten- oder Klassifikationsstelle** — jede Stelle vergleicht Literal-Strings.
- **`VerarbeitungUngeklärt` wird an 16 Stellen gesetzt** (alle in `ScmEventOrchestrator.cs`): Diagnose-Meldung des Kanals, Aktions-ID-Kollision, gescheiterte Outbox-Aktion, Kanal-Lesefehler (`IOException`/`UnauthorizedAccessException`/`JsonException`), Timeout/Sitzungsende nach `Zugestellt`/`InBearbeitung` (u. a. Reason „Korrelierter Abschluss fehlt oder CLI-Sitzung beendet.", Zeilen 587–597 bzw. 958–968). Rückweg nur manuell: `ResendAsync` → `"Aufgenommen"` oder `CancelAsync` → `"Abgebrochen"`.
- **Die PR-Verknüpfung hängt am `Accepted`-Block**: `LinkReportedPullRequestAsync` (Zeilen 976–991) wird in `ReconcileAttemptAsync` nur innerhalb `if (messages.Accepted is not null)` aufgerufen (Zeilen 578–579). Fehlt `accepted.json` oder endet das Ereignis vorher `VerarbeitungUngeklärt`, wird `messages.Complete.PullRequestNumber` nie ausgewertet — obwohl `ScmEventExchangeProtocol.ReadAsync` `complete.json` bereits unabhängig von `accepted.json` einliest (Zeile 359) und das Feld `ScmExchangeComplete.PullRequestNumber` existiert (Zeile 65).
- **`PullRequestReferenceService.SaveReportedAsync`** (Zeilen 93–149) ist der idempotente Registrierungspfad (Rolle `CreatedByTask`); eine fremd zugeordnete Referenz wird mit `null` quittiert statt übernommen. Im Aufbereitungspfad (`ReconcilePreparationAttemptAsync`) wird `PullRequestNumber` nicht ausgewertet — bestätigt die Annahme der Anforderung.
- **Reihenfolge-Regel**: `DispatchCoreAsync` (Zeile 182–186) blockiert die Zustellung eines Ereignisses, solange ein früheres Ereignis derselben Aufgabe (kleinere `Sequence`) nicht `Verarbeitet`/`Abgebrochen` ist — `VerarbeitungUngeklärt` blockiert damit auch Folgeereignisse.
- **Wartezeit/Auto-Abschluss**: `WorkItem.ScmCompletionDetectedUtc` (DB-Spalte `ScmAbschlussErkanntUtc`) + `ScmCompletionReference` (Spalte `ScmAbschlussReferenz`); Schalter `scm.taskcompletion.enabled` (Default an), `scm.taskcompletion.scope` (`ScmTaskCompletionCheckMode`), `scm.taskcompletion.wait.minutes` (Default 60) in `AppSettingService`.
- **Test-Ausgangszustand**: Build `Softwareschmiede.slnx` erfolgreich (0 Fehler/0 Warnungen, kein App-Lock). Unit-Tests: **2721 erfolgreich / 0 fehlgeschlagen / 3 übersprungen**; Integrationstests: **357 erfolgreich / 0 fehlgeschlagen / 0 übersprungen** (jeweils `--filter "Category!=OsInterface"`, `SOFTWARESCHMIEDE_SKIP_CONPTY_TESTS=1`). Testlücke: die komplette `OsInterface`-Spur (E2E/ConPTY/Clipboard u. a., darunter `E2E_ScmEvents`) wurde nicht ausgeführt. Details: [Tests](inventory/tests.md).
