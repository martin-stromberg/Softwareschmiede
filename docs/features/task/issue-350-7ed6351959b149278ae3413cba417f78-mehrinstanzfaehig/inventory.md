# Bestandsaufnahme: Mehrinstanzfähigkeit der SCM-Ereignisüberwachung (GitHub Issue #350)

Analysiert wurde der SCM-Ereignisverarbeitungspfad (Beobachtung → Validierung → Inbox/Store → Dispatch) sowie das GitHub-Plugin und die zugehörigen Teststrukturen, bezogen auf die Anforderung einer instanzübergreifenden Duplikaterkennung über die remote sichtbare Kontoreaktion (`requirement.md`).

## Zusammenfassung

- **Kein Remote-Reaktionskriterium vorhanden:** `ScmEventObservation` (`src/Softwareschmiede.Plugin.Contracts/Domain/ValueObjects/ScmEvents.cs`, Z. 30–49) enthält keinerlei Reaktionsinformation. Ein `ViewerHasReacted`-Flag oder eine Reaktionsliste existiert nicht; `reactionGroups`/`viewerHasReacted` kommt im gesamten Code nicht vor.
- **Ein GraphQL-Fragment für alle Textquellen:** `GitHubPlugin.TextFields` (`plugins/Softwareschmiede.Plugin.GitHub/GitHubPlugin.Events.cs`, Z. 13) ist die einzige Feldliste, die für `Description`-, Review- und je-Kommentar-`node`-Abfragen verwendet wird. Reaktionsdaten würden dort einmalig ergänzt; Kommentar-Beobachtungen laufen ohnehin je Kommentar über eine `node(id:)`-Abfrage (Z. 102–104), es entsteht kein zusätzlicher Request. `AddObservation` (Z. 232–258) befüllt alle Positionsparameter der Beobachtung zentral — der `ScmEventObservation`-Record wird dort an genau einer Stelle konstruiert.
- **Schreibpfad der Empfangsreaktion existiert:** `ScmEventOrchestrator.DispatchCoreAsync` (Z. 95–101) setzt für Nicht-`Description`-Beobachtungen die `receipt`-Aktion `ScmResponseKind.Reaction`/`"eyes"` über `ScmEventOutbox.EnsureAsync`/`ExecuteAsync`; `GitHubPlugin.EventResponses.cs` implementiert Ausführung (`ExecuteResponseAsync`, Z. 39–77) und Wiederfinden (`ReconcileResponseAsync`, Z. 10–36) inkl. REST-`ReactionEndpoint` (Z. 142–153) und GraphQL-Review-Pfad (`ReconcileReviewReactionAsync`, Z. 79–107). Damit existiert das remote sichtbare Merkmal, das die zweite Instanz erkennen soll — es wird aber nur geschrieben, nie beim Lesen ausgewertet.
- **Eingangsablehnung geht ausschließlich über `ScmEventValidationService.GetRejection`** (`src/Softwareschmiede/Application/Services/ScmEventValidationService.cs`, Z. 29–51): statischer Aufruf mit fünf bestehenden Ablehnungsgründen (Literal `"Kein Trigger"`, Konstante `KeineErwaehnungRejection`, `"Angemeldeter Benutzer ist nicht Repository-Owner"`, `"Bearbeiter nicht bestimmbar"`, `"Textversion stammt nicht vom Repository-Owner"`, `"Eigene Antwort"`). Ein Ablehnungsgrund für „bereits mit dem Konto reagiert" fehlt.
- **Ablehnung → Snapshot-Diagnose ohne Inbox:** `ScmEventStore.AcceptBatchAsync` (Z. 41–98) persistiert einen Ablehnungsgrund als `ScmContentSnapshot.Diagnostic`; nur bei `rejection is null` und freiem `EventKey` entsteht ein `ScmIncomingEvent`. Der Pfad für die geforderte Wirkung (kein Inbox-Eintrag, Checkpoint/Watermark läuft weiter) existiert bereits.
- **Dispatch-Gegenprüfung ist tolerant, nicht beliebig:** `DispatchCoreAsync` ruft `GetRejection` mit aktualisiertem Repository erneut auf (Z. 137–141); nur `"Kein Trigger"` und `KeineErwaehnungRejection` werden toleriert, jeder andere Ablehnungsgrund führt zu `WaitAsync` („Angemeldeter Benutzer ist nicht mehr der bestätigte Repository-Owner."). Ein neuer Ablehnungsgrund müsste dort bewusst eingeordnet werden — wobei die Revalidierung nur den **gespeicherten** Observationsstand prüft, keine Remote-Erneuerung (offene Frage der Anforderung).
- **Lokale Deduplikation bleibt wie beschrieben:** `EventKey` = `ContentKey/Revision/BodyHash` (Z. 42–48 in `ScmEvents.cs`), `ScmContentSnapshots` pro `ContentKey`, `ScmObservationCheckpoints` pro Quellschlüssel — alles instanzlokal, keine instanzübergreifende Komponente vorhanden.
- **Test-Ausgangszustand:** Alle vier Lanes ausgeführt. 2 nachgewiesene Fehlschläge, beide Zwischenablage-bezogene WPF-Tests in `TerminalControlTests` und fachlich unabhängig vom SCM-Bereich (Details und Nachweise: [Tests](inventory/tests.md)). Der konsolidierte SCM-E2E-Test `ScmEventsE2ETests.ScmEvents_QueueReceptionDispatchAndReplies_UseRealPipeline` lief **erfolgreich** — die Umgebung hat eine interaktive Desktop-Session, E2E-Erweiterungen sind damit hier lauffähig. 5 ConPTY-/Simulator-E2E-Tests übersprungen via `SOFTWARESCHMIEDE_SKIP_CONPTY_TESTS=1` (dokumentierte Sandbox-Auflage), 1 Nicht-Windows-Test erwartbar übersprungen.
- **Test-Lücke für die Anforderung:** Kein Test prüft bisher Reaktionsdaten beim Lesen — `FakeGitHubEventApi`-GraphQL-Antworten und das `ScmE2EApiClient`-`Node()` liefern keine `reactionGroups`-Felder; ein Kommentar mit vorhandener Viewer-Reaktion ist als Szenario nicht darstellbar.
