# Umsetzungsplan: Terminalintegration verbessern — gemeinsame PTY-Session und sauberes VT-Rendering

## Übersicht

Die interaktive KI-CLI-Einbettung wird auf eine gemeinsame Session-Abstraktion `ITerminalSession` umgestellt: Prozessstart, ConPTY-/Pipe-Erzeugung, `Resize`, Ein-/Ausgabe, Exit-/Fehler-Ereignisse und der Session-Lebenszyklus werden in einer zentralen `ITerminalSessionFactory`/`TerminalSessionService` gebündelt. Der heutige Umweg „cmd.exe in der ConPTY starten → Plugin-Befehl ~300 ms später als Tastaturbytes injizieren" (`Win32PseudoConsoleProcessLauncher.Start` + `KiAusfuehrungsService.SendCommandDelayedAsync`) entfällt; die Anbieter-CLI wird direkt aus einer `TerminalSessionStartSpec` gestartet, die die Plugins über `IKiPlugin.GetTerminalStartSpecAsync` liefern. Da `CreateProcess` nur `.exe`-Namen ohne PATHEXT auflöst und `.cmd`/`.bat` nicht laden kann, ersetzt ein `TerminalExecutableResolver` die bisherige Shell-Auflösung: nackte Befehlsnamen werden mit PATHEXT-Semantik aufgelöst, `.cmd`/`.bat`-Ziele werden zu `cmd.exe /d /s /c` normalisiert — die Launcher erhalten eine bereits `CreateProcess`-fähige Spec. Der VT-Renderer (`AnsiSequenceParser` + `TerminalBuffer` + `TerminalControl`) wird um die fehlenden Sequenzen (Alternate Screen, Insert/Delete Line/Char, Scroll-Regionen, chunk-übergreifendes UTF-8 u. a.) erweitert; der Pipe-Pfad bleibt als explizit diagnostizierter Fallback erhalten; ein begrenzter `TerminalReplayBuffer` sichert die UI-Neuanbindung. Als erste produktive CLIs werden **`DevinPlugin` und `CodexPlugin`** migriert und validiert; `KiSimulatorPlugin` bleibt der E2E-/Test-Anbieter und wird dafür auf eine **interaktive `cmd.exe /k`-Shell** umgestellt, damit prompt-basierte E2E-Mechanismen (echo-Marker, Eingabe, `exit`) unter Direct-Start weiter funktionieren.

## Designentscheidungen

| Komponente / Bereich | Gewählter Ansatz | Begründung |
|----------------------|-----------------|------------|
| Lage von `ITerminalSession` | `Softwareschmiede.Infrastructure.Terminal` (neben `PseudoConsoleSession`) | Plugins kennen die Session nicht — sie liefern nur die Startbeschreibung. Das Contracts-Projekt bleibt frei von Laufzeittypen (`Stream`, `TerminalBuffer`). Alle Konsumenten (`KiAusfuehrungsService`, App-Layer) haben bereits Zugriff. |
| Umfang von `ITerminalSession` | Vertrag aus der Anforderung (`WriteInputAsync`, `Resize`, `OutputChunk`, `Exited`, `Failed`, `IDisposable`) **plus** die von allen Konsumenten benötigte Oberfläche (`Buffer`, `BufferChanged`, `RuntimeStatus`, `RuntimeStatusChanged`, `WritePromptAsync`, `DrainOutputAsync`, `MarkInputActivity`, `IsPseudoTerminal`, `RebuildBufferFromReplay`) | `TerminalControl`, `CliProcessManager`, `PromptZeitVersandService`, `TaskDetailViewModel` und die Test-Doubles brauchen diese Member bereits; ein weiteres Sub-Interface nur für den Renderer wäre unnötige Zerteilung (kein PoEAA-Mehrwert, reine Interface-Segregation ohne zweiten Implementierer). |
| Session-Erzeugung | Neue zentrale `ITerminalSessionFactory`/`TerminalSessionService` in `Softwareschmiede.Infrastructure.Terminal`; `IPseudoConsoleProcessLauncher` bleibt als **interne Backend-Naht** mit geänderter Signatur (direkter Start aus `TerminalSessionStartSpec`, Rückgabe `TerminalSessionStartResult`) | Die Naht ist bereits der Test-/E2E-Austauschpunkt (4 Test-Doubles + `SimulatedPseudoConsoleProcessLauncher`). Sie zu erhalten minimiert DI- und Test-Umbau; die Factory entscheidet Backend-Wahl (PTY vs. Pipe) anhand von Preflight + Capabilities. |
| Spec-Beschaffung (eindeutiger Weg) | Der Service ruft ausschließlich `IKiPlugin.GetTerminalStartSpecAsync(localRepoPath, parameters, ct)` auf — die Interface-Methode ist der einzige vertragliche Spec-Weg. `CliKiPluginBase` implementiert sie nicht-abstrakt und delegiert intern auf `BuildTerminalStartSpec`, das `BuildProcessStartInfo` auf die Spec mappt. `StartCliAsync`/`ProcessStartInfo` bleibt **nur** für den klassischen, nicht-interaktiven Pipe-Pfad (`KiAusfuehrungsService.StartCliAsync`) erhalten. Kein Cast auf `CliKiPluginBase` im Service. | Auflösung des doppelten Beschaffungswegs: `BuildProcessStartInfo` ist bereits faktisch die Startbeschreibung — die Plugins bleiben nahezu unverändert, nur die Capabilities-Eigenschaft kommt hinzu. Ein Interface-Member vermeidet die Abhängigkeit des Services auf die Basisklasse und lässt Nicht-`CliKiPluginBase`-Plugins ebenfalls eine Spec liefern. |
| Anbieterfähigkeiten | `[Flags]`-Enum `TerminalProviderCapabilities` (`SupportsPty`, `RequiresPty`) als virtuelle Property an `CliKiPluginBase`, in `IKiPlugin` deklariert; Standard `SupportsPty`. Festgelegte Werte: TUI-CLIs (`ClaudeCliPlugin`, `CodexPlugin`, `GitHubCopilotPlugin`, `DevinPlugin`) → `RequiresPty \| SupportsPty`; `KiSimulatorPlugin` → `SupportsPty` (Default reicht, kein Override nötig) | Deklarativ pro Plugin (vom Anwender bestätigt). `RequiresPty` = CLI verweigert/versagt ohne echte TTY → kein Pipe-Fallback erlaubt, sondern klare Fehlerdiagnose. `SupportsPty` bleibt zusätzlich gesetzt, damit die CLI auf PTY läuft, wenn verfügbar. |
| Backend-Wahl und Priorität | Feste Entscheidungsreihenfolge in `TerminalSessionService.StartAsync`: **(1)** `RequiresPty` gesetzt **und** Preflight meldet PTY nicht verfügbar → harter Fehler (gilt auch im E2E-Modus); **(2)** E2E-Modus (`SOFTWARESCHMIEDE_TEST_DB_PATH` gesetzt) → Pipe-Backend (`SimulatedPseudoConsoleProcessLauncher`); **(3)** Capability ohne `SupportsPty` → Pipe + Diagnose; **(4)** PTY verfügbar → `Win32PseudoConsoleProcessLauncher`, sonst Pipe + Diagnose. **Kein Benutzer-/Konfigurations-Toggle** — die Wahl ist ausschließlich automatisch (vom Anwender bestätigt) | Die Reihenfolge löst den Prioritätskonflikt konkret: Der `RequiresPty`-Fehler prüft das **Preflight-Ergebnis** (echte oder per Test-Override erzwungene PTY-Verfügbarkeit), nicht das gewählte Backend — deshalb funktioniert im E2E-Modus ein `RequiresPty`-Plugin weiter auf dem simulierten Pipe (Preflight auf dem Testrechner = PTY verfügbar), sodass z. B. der `PluginAuswahlUndWechsel`-E2E (Wechsel zu einem `RequiresPty`-Plugin — konkret `Softwareschmiede.Codex` mit geseedetem `ExecutablePath`, siehe „Bestehende E2E-Anpassungen") weiterläuft; gleichzeitig bleibt der Fehlerfall per Override-Erzwingung in derselben App-Instanz testbar. Der Fallback ist ein erster Bürger mit eigener, sichtbarer Session statt des unsichtbaren `StartCliAsync`-Pfads; er wird immer diagnostiziert (Log + `CliOutput`-Markerzeile), nie stillschweigend. |
| Preflight-Test-Override (E2E-Auslöser) | **`TerminalSessionService`** liest den `AppEinstellungen`-Schlüssel `Terminal.ForcePtyUnavailable` (`"true"`) pro Start über `IServiceScopeFactory` + `AppEinstellungService` (gleiches Scope-Pattern wie `KiAusfuehrungsService`) und übergibt das Ergebnis als Parameter `forcePtyUnavailable` an `TerminalSessionDiagnostics.RunPreflightAsync`. `TerminalSessionDiagnostics` selbst greift nicht auf die Datenbank zu. Gesetzt → der PTY-Verfügbarkeits-Check schlägt fehl (`Ok=false`, Detail „durch Test-Override erzwungen") | Der Schlüssel lässt sich **innerhalb** eines laufenden E2E-App-Lifecycles über `OpenTestDbContext` schreiben/löschen (etabliertes Seeding-Muster wie in `E2E_SessionLimitPause`). Eine Umgebungsvariable wäre nur beim Prozessstart wirksam und erforderte einen zweiten App-Launch — entfällt damit. Das Lesen liegt im Service statt in der Diagnose, damit `TerminalSessionDiagnostics` DB-frei bleibt und der Override in `TerminalSessionDiagnosticsTests` als reiner Parameter deterministisch testbar ist. Der Hook ist bewusst als Debug-/Test-Mechanismus dokumentiert und greift nie implizit. |
| Preflight-Health-Check (`CheckHealthAsync`) | `ITerminalSessionFactory.StartAsync` erhält einen Parameter `Func<CancellationToken, Task<bool>>? healthCheck`; `KiAusfuehrungsService.StartTerminalSessionAsync` übergibt `kiPlugin.CheckHealthAsync` als Methodengruppe. `TerminalSessionDiagnostics.RunPreflightAsync(spec, resolution, healthCheck, forcePtyUnavailable, ct)` ruft den Delegate **nur** auf, wenn der Executable-Check nicht bereits fehlgeschlagen ist (`NotFound`/`NotExecutable` → Check als „übersprungen" protokolliert); `false`-Ergebnis oder geworfene Exception → `Ok=false` mit Detail als **reiner Diagnoseeintrag ohne Einfluss auf `BackendEmpfehlung`** | `CheckHealthAsync` ist eine `IKiPlugin`-Instanzmethode (`CliKiPluginBase.cs:181`) — die Factory/die Diagnose kennen das Plugin bewusst nicht (Pluginfreiheit bleibt auf Spec-Ebene erhalten); ein Delegate hält die Signaturen vom Contracts-Typ frei und ist in Tests trivial fälschbar (`ct => Task.FromResult(true)` oder `null`). Überspringen bei gescheiterter Auflösung spart die bis zu 10 s lange `--version`-Probe eines nachweislich fehlenden Kommandos. Nicht-fatal, weil `CheckHealthAsync` intern `Process.Start` ohne Resolver nutzt und bei `.cmd`-Installationen falsch negativ ausfallen kann — die eigentliche Startfähigkeit sichert der Resolver-Check unabhängig ab; der Health-Check liefert Versions-/Diagnoseinformation. |
| Test-Austauschpunkt `ITerminalSessionFactory` | `KiAusfuehrungsService`-Konstruktor erhält `ITerminalSessionFactory` als **Pflichtparameter** (statt `IPseudoConsoleProcessLauncher?` mit `Win32…`-Default). Tests injizieren ein neues Double `TestTerminalSessionFactory` (`Softwareschmiede.Tests/Helpers`), das `StartAsync` an einen übergebenen `IPseudoConsoleProcessLauncher` delegiert (die bestehenden Launcher-Doubles `Deterministic*`/`FixedOutput*`/`OutputByTask*`/`DelayedOutput*` bleiben wiederverwendbar); ohne Launcher erzeugt es die bisherige deterministische In-Memory-Session. Konsequenz: `KiAusfuehrungsServiceTests` lassen den echten `TerminalExecutableResolver` **nicht** mitlaufen — Specs mit `FileName = "exit"`/`"echo"` bleiben opaque Testdaten; die Auflösung wird ausschließlich in `TerminalExecutableResolverTests`/`TerminalSessionServiceTests` gegen echte/auflösbare Executables (`cmd.exe`, Temp-PATH-Fixtures) geprüft | `TerminalSessionService` kann nicht default-konstruiert werden (braucht Options, beide Launcher, ScopeFactory) — ein Pflichtparameter macht die Abhängigkeit ehrlich. Die Double-Delegation an die vorhandene Launcher-Naht hält den Umbau der ~20 Service-Test-Aufrufstellen minimal (`new TestTerminalSessionFactory(launcher)` statt `launcher`). Resolver-Durchlauf in Service-Tests würde alle Builtin-Specs (`"exit"`, `"echo"`) zu `NotFound` machen — ohne Mehrwert, da Auflösung/Backend-Wahl eigene Testklassen haben. |
| Launcher-Injektion in `TerminalSessionService` | Konstruktorparameter `IPseudoConsoleProcessLauncher ptyLauncher, IPseudoConsoleProcessLauncher pipeLauncher` (interface-typisiert, Rollen über Parameternamen); `App.xaml.cs` registriert `ITerminalSessionFactory` über eine Factory-Lambda, die die beiden konkret registrierten Launcher-Typen auflöst | Zwei `AddSingleton`-Registrierungen desselben Interface-Typs wären in der DI nicht unterscheidbar (kein keyed-Container-Muster im Projekt); konkrete Typregistrierung + Lambda-Auflösung folgt dem bestehenden Registrierungsmuster und erlaubt Double-Injektion in `TerminalSessionServiceTests` (beide Slots frei belegbar). |
| Executable-Auflösung für den Direct-Start | Neue interne Komponente `TerminalExecutableResolver` in `Softwareschmiede.Infrastructure.Terminal`, aufgerufen in `TerminalSessionService.StartAsync` **vor** dem Preflight: löst `spec.FileName` mit `where`-/PATHEXT-Semantik zu einer `CreateProcess`-fähigen, normalisierten `TerminalSessionStartSpec` auf und liefert `TerminalExecutableResolution` (Status `Direct`/`CmdWrapped`/`NotFound`/`NotExecutable` + `ResolvedPath`) für den Preflight-Executable-Check. `.exe`/endungslos gefundene Dateien → `FileName` = absoluter Pfad (Direct); `.cmd`/`.bat` → Normalisierung zu `FileName = "cmd.exe"`, `Arguments = "/d /s /c \"<aufgelöster Pfad>\" <Original-Arguments>"` (`CmdWrapped`, `/d` unterdrückt AutoRun — dieselbe Shell-Wrap-Technik wie die `/k`-Wahl des `KiSimulatorPlugin`, nur als Service-Normalisierung statt Plugin-Spec) | `CreateProcess` (in `PseudoConsoleProcessStarter`, und ebenso `Process.Start` im `SimulatedPseudoConsoleProcessLauncher`) sucht bei erweiterungslosen Namen nur `<name>.exe` (kein PATHEXT) und kann `.cmd`/`.bat` prinzipiell nicht als Image laden (ERROR_BAD_EXE_FORMAT). Die bisherige PATHEXT-/Shell-Auflösung über die getippte cmd.exe-Eingabe entfällt mit der Hülle — sie wird durch diese zentrale Auflösung ersetzt. Zentral im Service statt in den Plugins, weil (a) die Plugins bewusst weiterhin nackte Namen bzw. `.cmd`-Pfade liefern dürfen (`ResolveExecutablePath`-Defaults `"codex"`/`"copilot"`, `FindDevinExecutable`/`FindClaudeExecutable`, konfigurierter `ExecutablePath`), (b) beide Backends identische Semantik erhalten und (c) das Auflösungsergebnis direkt den Preflight-Check speist (Unterscheidung „nicht gefunden" vs. „gefunden, aber nicht ausführbar"). Auflösung gegen die effektive Spec-Umgebung (`PATH`/`PATHEXT` aus `spec.EnvironmentVariables`, sonst Prozess-Env), Suchreihenfolge `spec.WorkingDirectory` → `PATH`-Einträge (entspricht der cwd-zuerst-Semantik von cmd.exe/CreateProcess). Semantik angelehnt an den bestehenden `CliRunner.ResolveExecutablePath`-Präzedenzfall (PATH + `.exe`/`.cmd`/`.bat`), ohne dessen `gh`-spezifische Known-Dirs. |
| Interaktives Test-CLI unter Direct-Start | `KiSimulatorPlugin.BuildProcessStartInfo` liefert `cmd.exe /k "echo KI-Simulator läuft..."` — eine **interaktive cmd.exe-Shell** statt des `cmd.exe /c`-One-Shots. `/k` führt das Banner-Kommando aus und bleibt danach geöffnet: stdin wird zeilenweise als Befehle gelesen (Pipe-Pfad: `CrSubmittingInputStream` übersetzt `\r`→`\r\n`; PTY-Pfad: ConPTY-Tastatursemantik). `ping -n 31` entfällt — die Shell terminiert nicht mehr selbst; `exit`/`exit /b <code>` als Prompt beendet sie deterministisch mit steuerbarem Exit-Code | Ohne diese Änderung verlieren alle prompt-basierten E2E-Mechanismen ihre Ausführungsgrundlage (`cmd.exe /c` ignoriert stdin und beendet sich nach ~30 s): Rate-Limit-`echo`-Marker, `WritePromptAsync`-Flüsse, ANSI-/Burst-Ausgaben per Prompt. `/k` ist die minimale, produktionsnahe Lösung — gleiche Shell-Semantik wie die bisherige äußere interaktive cmd.exe-Hülle, nur jetzt als Spec-Eigentum des Plugins statt als Launcher-Umweg. Seiteneffekt: Befehle werden sofort statt nach der ~30-s-`ping`-Blockade ausgeführt — Wartelogiken verkürzen sich. |
| cmd.exe-Hülle im Launcher | Vollständig entfernt: `SendCommandDelayedAsync`, `BuildCliCommand`, `CliProcessHandle.SendCts` werden gelöscht; beide Launcher starten `spec.FileName` direkt | Die Anforderung ersetzt die Injektion durch direkten Start; CLIs ohne PTY-Fähigkeit gehen in den Pipe-Fallback, nicht in eine cmd.exe-Verschachtelung. Dass `KiSimulatorPlugin` selbst `cmd.exe /k` als Executable wählt, ist dessen eigene CLI-Wahl — keine Launcher-Hülle. |
| Renderer-Strategie | Bestehender Stack `AnsiSequenceParser` + `TerminalBuffer` + `TerminalControl` wird erweitert (Annahme aus der Anforderung) — **kein** `xterm.js`/WebView2 | WebView2-Hosting wäre ein architektonischer Bruch (neuer Prozess, neuer Kommunikationskanal, neuer Eingabepfad). Der Eigenbau deckt bereits SGR/256er/TrueColor/Cursor/Clear/Erase; die dokumentierten Lücken sind gezielt schließbar. Zudem bleibt das Parsen auf dem Lese-Thread — wichtig für „schnelle Output-Bursts blockieren die UI nicht". |
| `Exited`/`ExitCode` | Session besitzt das native Prozess-Handle (`IntPtr`, optional) und löst `Exited` mit dem via `GetExitCodeProcess` ermittelten Code aus; `CliProcessHandle.NativeProcessHandle` entfällt | Zentralisiert den Lebenszyklus in der Session (Anforderung) und behält die PID-Wiederverwendungs-sichere Exit-Code-Ermittlung. |
| `OutputChunk` vs. `ITerminalOutputSink` | Beides bleibt: `OutputChunk`-Event als öffentliches Vertrags-Element; `ITerminalOutputSink` bleibt die konstruktor-injizierte Senke für `CliOutputProtokollWriter` (mit `Complete`/`CompleteAsync`-Lebenszyklus) | Die Senke hat ein Abschluss-Protokoll mit Drain-Semantik, das ein `event` nicht abbildet; das Event trägt `ReadOnlyMemory<byte>` (Span ist in EventArgs nicht möglich) und versorgt Diagnose/weitere Konsumenten. |
| Replay-Form | Rohe Byte-Chunks im `TerminalReplayBuffer` (Ringpuffer mit Byte-Budget, konfigurierbar über `TerminalSessionOptions.ReplayBufferByteBudget`, **Default 512 KB** — vom Anwender bestätigt); bei UI-Neuanbindung baut die Session ihren `TerminalBuffer` synchron aus den gespeicherten Chunks neu auf (`RebuildBufferFromReplay`, frischer `AnsiSequenceParser`, unter demselben Render-Lock wie die Leseschleife) | Ein kanonischer Buffer bleibt erhalten (kein Divergieren zwischen Live- und Replay-Puffer, keine doppelten Ausgaben); Neu-Parsen garantiert korrekten Zustand auch nach Alt-Screen-/Resize-Wechseln. Getrennt vom dauerhaften `CliOutputProtokollWriter`-Protokoll. |
| `TerminalSessionOptions`-Bereitstellung | `services.Configure<TerminalSessionOptions>(context.Configuration.GetSection(TerminalSessionOptions.SectionName))` in `App.xaml.cs`; neue Sektion `"Terminal"` in `src/Softwareschmiede/appsettings.json` | Folgt dem bestehenden Options-Muster (`DirectoryStructureOptions`, `AutonomAufgabenOptions` werden identisch gebunden). Damit ist `ReplayBufferByteBudget` über `appsettings.json` konfigurierbar, ohne neue Konfigurationsinfrastruktur. |
| `TerminalSessionOptions`-Fluss zu den Konsumenten | **`IOptions<TerminalSessionOptions>`-Konstruktorparameter** an drei Stellen: `TerminalSessionService` (liest `DefaultCols`/`DefaultRows` für den Preflight-Größen-Check und validiert `ReplayBufferByteBudget > 0` defensiv vor dem Launcher-Aufruf), `Win32PseudoConsoleProcessLauncher` (`PseudoConsole.Create(DefaultCols, DefaultRows)` statt hartkodiert `220, 50`; übergibt `options.Value` an den `PseudoConsoleSession`-Konstruktor) und `SimulatedPseudoConsoleProcessLauncher` (übergibt `options.Value` an den `PseudoConsoleSession`-Konstruktor — Replay-Budget und initiale Buffer-Größe). Die `TerminalSessionStartSpec` bleibt frei von Größen-/Budget-Feldern; die Launcher-`Start`-Signatur ändert sich nicht | Die Werte sind Host-Laufzeitkonfiguration, keine Plugin-/Spec-Daten — Spec-Felder würden sie dem Plugin zuschreiben, dem sie nicht gehören. Ein `Start`-Parameter würde die bewusst minimal gehaltene Launcher-Signatur `(aufgabeId, spec, outputSink)` aufblähen. Konstruktor-Injektion von `IOptions` folgt dem Options-Muster und ist in der DI kostenlos: beide Launcher werden als konkrete Typen registriert, `IOptions<TerminalSessionOptions>` ist nach `services.Configure` automatisch auflösbar. Tests erzeugen die Launchers mit `Microsoft.Extensions.Options.Options.Create(new TerminalSessionOptions())` bzw. übergeben `new TerminalSessionOptions()` an Session-Aufrufstellen. |
| Plattformscope | Windows/ConPTY only; `ITerminalSession`/Backend-Naht lässt spätere PTY-Backends zu | Anforderung nennt `node-pty` nur referenziell; die App ist Windows-only (`net10.0-windows10.0.17763.0`). |
| Session-Neuanbindung | Bezieht sich auf UI-Neuanbindung (`TerminalControl.Session`-Wechsel beim Seiten-Navigation); App-Neustart/Detach bleibt außerhalb des Scopes | Heutiger Mechanismus (laufende Session überlebt Navigation) bleibt Basis; Replay ersetzt die blanke Buffer-Übernahme. |
| `CliSessionService`/`ICliSessionService` | Löschen (toter Code: keine DI-Registrierung, keine Aufrufer) | Anforderung erlaubt Abbau; der zeilenbasierte `ReadLineAsync`-Pfad darf ohnehin nicht im interaktiven Pfad existieren. Fallback-Rolle übernimmt der Pipe-Backend-Pfad der Factory. |

## Programmabläufe

### Interaktiver CLI-Start über `ITerminalSession` (PTY-Pfad)

1. Aufrufer (`EntwicklungsprozessService.ProzessStartenUndCliStartenAsync`/`CliNeustartenAsync`, `ProjektleiterAgentService.StarteAgentAsync`) ruft `KiAusfuehrungsService.StartTerminalSessionAsync` (umbenannt aus `StartWithPseudoConsoleAsync`).
2. `KiAusfuehrungsService` serialisiert über `_startLock`, prüft auf bereits laufendes Handle, löst `WorkingDirectoryResolver.DetermineEffectiveWorkingDirectoryAsync` auf.
3. `kiPlugin.GetTerminalStartSpecAsync(localRepoPath, parameters, ct)` liefert die `TerminalSessionStartSpec` — Interface-Weg, kein Basisklassen-Cast. In `CliKiPluginBase` mappt `BuildTerminalStartSpec` das `BuildProcessStartInfo`-Ergebnis (FileName, Arguments, WorkingDirectory, EnvironmentVariables) plus `TerminalCapabilities` und `PluginName` auf die Spec.
4. `ITerminalSessionFactory.StartAsync(aufgabeId, spec, outputWriter, kiPlugin.CheckHealthAsync, ct)` → `TerminalSessionService` (der `healthCheck`-Delegate entkoppelt die Factory vom Plugin — `CheckHealthAsync` ist `IKiPlugin`-Instanzmethode und wird nur als aufrufbare Probe durchgereicht):
   a. Liest `IOptions<TerminalSessionOptions>` und den `Terminal.ForcePtyUnavailable`-Schlüssel aus `AppEinstellungen` (Scope via `IServiceScopeFactory`/`AppEinstellungService`) → `bool forcePtyUnavailable`.
   b. `TerminalExecutableResolver.Resolve(spec)` löst `spec.FileName` auf und liefert `TerminalExecutableResolution` (normalisierte Spec + Status): Suchreihenfolge `spec.WorkingDirectory`, dann alle Einträge des effektiven `PATH` (aus `spec.EnvironmentVariables`, sonst Prozess-Env); `FileName` mit Verzeichnisanteil → nur dieses Verzeichnis (relativ gegen `WorkingDirectory`); `FileName` mit Erweiterung → nur literal gesucht, ohne Erweiterung → PATHEXT-Liste angehängt (`spec.EnvironmentVariables["PATHEXT"]`, sonst Prozess-Env, sonst `.COM;.EXE;.BAT;.CMD`). Treffer `.exe`/endungslos → `Direct` (Spec-FileName = absoluter Pfad); Treffer `.cmd`/`.bat` → `CmdWrapped` (Spec-FileName = `cmd.exe`, Arguments = `/d /s /c "<pfad>" <original>`); Treffer mit sonstiger Erweiterung (z. B. `.ps1`) → `NotExecutable`; kein Treffer → `NotFound`.
   c. `TerminalSessionDiagnostics.RunPreflightAsync(spec, resolution, healthCheck, forcePtyUnavailable, ct)` prüft und protokolliert: OS-Build ≥ 17763 (ConPTY-Verfügbarkeit; bei `forcePtyUnavailable` erzwungen fehlschlagend), Executable — aus dem Auflösungsergebnis (`Direct`/`CmdWrapped` → `Ok` mit `ResolvedPath` als Detail; `NotFound` → `Ok=false` „nicht gefunden"; `NotExecutable` → `Ok=false` „gefunden, aber nicht CreateProcess-ausführbar"), CLI-Version/Health — der `healthCheck`-Delegate wird **nur bei erfolgreicher Executable-Auflösung** aufgerufen (`NotFound`/`NotExecutable` → Einzelcheck als „übersprungen" markiert; die `--version`-Probe eines fehlenden Kommandos würde sonst sinnlos bis zu 10 s warten); Ergebnis `false`/Exception → `Ok=false` mit Detail, **ohne Einfluss auf `BackendEmpfehlung`** (reiner Diagnoseeintrag — `CheckHealthAsync` nutzt intern `Process.Start` ohne Resolver und kann bei `.cmd`-Installationen falsch negativ ausfallen; die Startfähigkeit ist bereits durch den Executable-Check gesichert), Encoding (UTF-8), initiale Terminalgröße (Default 220×50 aus Options), übergebene Pluginparameter. Ergebnis: `TerminalPreflightResult` mit Einzelprüfungen, `PtyVerfuegbar` und Backend-Empfehlung.
   d. `NotFound`/`NotExecutable` → `BackendEmpfehlung = Fehler`: Diagnose-Marker schreiben (Schritt 6) + `InvalidOperationException` — kein Pipe-Fallback, da dieselbe Spec auch auf dem Pipe-Backend nicht starten würde.
   e. Backend-Wahl in fester Reihenfolge: (1) `RequiresPty && !PtyVerfuegbar` → Diagnose-Marker + `InvalidOperationException`; (2) E2E-Modus → `SimulatedPseudoConsoleProcessLauncher`; (3) `!SupportsPty` → Pipe + Diagnose; (4) `PtyVerfuegbar` → `Win32PseudoConsoleProcessLauncher.Start(normalizedSpec)` → `PseudoConsole.Create(_options.DefaultCols, _options.DefaultRows)` (statt hartkodiert `220, 50`) → `PseudoConsoleProcessStarter.Start(psi, conpty)` startet die **Anbieter-CLI direkt** (kein cmd.exe — es sei denn, die Auflösung hat ein `.cmd`/`.bat`-Ziel normalisiert zu `cmd.exe /d /s /c`) → `PseudoConsoleSession` mit `nativeProcessHandle` und `options.Value`; sonst → Pipe + Diagnose (`SimulatedPseudoConsoleProcessLauncher` erzeugt die `PseudoConsoleSession` ebenfalls mit `options.Value`). Beide Launcher erhalten ausschließlich die **normalisierte** Spec, enthalten keine eigene Auflösungslogik und beziehen die Options-Werte aus ihrem `IOptions<TerminalSessionOptions>`-Konstruktorparameter (nicht aus der Spec, nicht aus der `Start`-Signatur).
5. `KiAusfuehrungsService` legt `CliProcessHandle` mit `Session` (`ITerminalSession`) an, abonniert `session.Exited`/`session.Failed` → `HandleProcessExitedAsync`, trägt Handle in `_handles` ein, feuert `CliProcessStatusChanged(Gestartet)`.
6. Bei jedem Nicht-PTY-Backend sowie bei jedem Preflight-Fehlschlag: Diagnose wird geloggt **und** als `CliOutput`-Protokollzeile persistiert. Schreibweg konkret: `TerminalSessionService` ruft `outputSink?.OnOutputChunk(Encoding.UTF8.GetBytes("[Terminal-Diagnose] <Grund> | Checks: <Einzelergebnisse>\r\n"))` auf — `\r\n` terminiert die Zeile für den `CliOutputLineAccumulator` im `CliOutputProtokollWriter`. Der Marker geht **nur** an die Protokoll-Senke: Er landet im `CliOutput`-Protokoll, aber nicht im `TerminalReplayBuffer`/`TerminalBuffer` und damit weder in der Terminal-Anzeige noch im Reattach-Replay (es ist eine Diagnose-Protokollzeile, keine CLI-Ausgabe). Im Fehlerfall (`RequiresPty`, `NotFound`, `NotExecutable`) wird der Marker **vor** dem Werfen der Exception geschrieben — der `CliOutputProtokollWriter` existiert bereits (`KiAusfuehrungsService` erzeugt ihn vor dem Factory-Aufruf), und dessen `CompleteAsync` im catch-Pfad flusht die gequeuete Zeile noch vor dem Schließen (Marker-Präfix „[Terminal-Diagnose]" mit Grund und Einzelcheck-Ergebnissen, u. a. `PtyVerfuegbar=false`).

Beteiligte Klassen/Komponenten: `KiAusfuehrungsService`, `ITerminalSessionFactory`/`TerminalSessionService`, `TerminalExecutableResolver`, `TerminalExecutableResolution`, `TerminalSessionDiagnostics`, `TerminalSessionStartSpec`, `TerminalSessionOptions`, `AppEinstellungService` (Test-Override), `IPseudoConsoleProcessLauncher` (beide Implementierungen), `PseudoConsole`, `PseudoConsoleProcessStarter`, `PseudoConsoleSession`, `CliProcessHandle`, `CliOutputProtokollWriter`, `CliKiPluginBase`, `IKiPlugin`.

### Ausgabe-Streaming (Rohdatenpfad)

1. `PseudoConsoleSession.ReadLoopAsync` liest 4096-Byte-Chunks aus `OutputStream`.
2. Pro Chunk in dieser Reihenfolge: `MarkOutputActivity` → `TerminalReplayBuffer.Append` → `_outputSink?.OnOutputChunk` (Protokoll) → `OutputChunk`-Event → `AnsiSequenceParser.Parse` → `Buffer.Apply` pro `TerminalEvent` (unter Render-Lock) → `BufferChanged`.
3. `TerminalControl` rendert aus `Buffer.GetSnapshot()` auf `BufferChanged` via `Dispatcher.InvokeAsync` (unverändert).
4. `CliOutputLineAccumulator` bleibt ausschließlich innerhalb `CliOutputProtokollWriter` (Protokollierung) — kein `ReadLine` im interaktiven Pfad.

Beteiligte Klassen/Komponenten: `PseudoConsoleSession`, `TerminalReplayBuffer`, `ITerminalOutputSink`, `CliOutputProtokollWriter`, `CliOutputLineAccumulator`, `AnsiSequenceParser`, `TerminalBuffer`, `TerminalControl`.

### Eingabe / Paste

Unverändert zentral über `TerminalControl` (`OnPreviewKeyDown`, `OnTextInput`, `ReadClipboardAndInsertAsync`) → `KeyToVt100Encoder` → `session.InputStream.Write` bzw. `session.WriteInputAsync`. Prompt-Versand (`PromptZeitVersandService`, `ProjektleiterAgentService.SendeInitialPromptVerzoegertAsync`) nutzt weiter `session.WritePromptAsync` — jetzt über den `ITerminalSession`-Typ.

Beteiligte Klassen/Komponenten: `TerminalControl`, `KeyToVt100Encoder`, `ITerminalSession`, `PromptZeitVersandService`, `ProjektleiterAgentService`.

### Interaktive Test-CLI (`KiSimulatorPlugin`) unter Direct-Start

1. `KiSimulatorPlugin.BuildProcessStartInfo` liefert `FileName = "cmd.exe"`, `Arguments = "/k \"echo KI-Simulator läuft...\""`, `WorkingDirectory = localRepoPath`, `UseShellExecute = false`.
2. Direct-Start startet eine interaktive cmd.exe-Instanz: `/k` führt `echo KI-Simulator läuft...` aus (sichtbares Banner in Ausgabe und `CliOutput`-Protokoll) und bleibt danach geöffnet.
3. `WritePromptAsync`/`WriteInputAsync` schreiben Befehlszeilen in stdin: Pipe-Pfad → `CrSubmittingInputStream` übersetzt das abschließende `\r` zu `\r\n`, cmd.exe führt die Zeile aus (z. B. `echo [[SOFTWARESCHMIEDE_RATE_LIMIT:…]]` → Marker im `CliOutput`-Protokollpfad → `KiPluginLimitService`); PTY-Pfad → ConPTY-Tastatursemantik, identische Bedienung.
4. Prozessende: deterministisch per Prompt `exit` bzw. `exit /b <code>` (steuerbarer Exit-Code für den `Exited`-Nachweis) oder per `Kill` über `StopCliAsync` (bestehender E2E-Weg).
5. Kein `ping -n 31` mehr: keine ~30-s-Blockade und keine Selbstterminierung — Prompts werden sofort ausgeführt, die Session lebt unbegrenzt bis zu `exit`/Kill.

Beteiligte Klassen/Komponenten: `KiSimulatorPlugin`, `CliKiPluginBase` (Spec-Mapping), `SimulatedPseudoConsoleProcessLauncher` (`CrSubmittingInputStream`), `Win32PseudoConsoleProcessLauncher`, `PseudoConsoleSession`, `CliOutputProtokollWriter`, `KiPluginLimitService`.

### Resize

1. `TerminalControl.OnRenderSizeChanged` → `buffer.Resize` + `session.Resize(cols, rows)` (bestehende Verdrahtung, bleibt).
2. `PseudoConsoleSession.Resize` dedupliziert: identische (cols, rows) wie zuletzt gesendet → No-Op; sonst serialisiert (Lock) an `IPseudoConsoleHandle.Resize` — verhindert konkurrierende/doppelte Resize-Aufrufe.

Beteiligte Klassen/Komponenten: `TerminalControl`, `PseudoConsoleSession`, `IPseudoConsoleHandle`.

### Session-Neuanbindung (UI-Reattach)

1. `TerminalControl.Session` wird gesetzt (`TaskDetailView.SetTerminalSession`, z. B. bei Navigation zurück auf eine Aufgabenseite).
2. `OnSessionChanged`: alte `BufferChanged`-Registrierung lösen; `session.RebuildBufferFromReplay()` — die Session setzt `Buffer` zurück (`TerminalBuffer.Reset`) und parst die gespeicherten `TerminalReplayBuffer`-Chunks synchron mit einem frischen `AnsiSequenceParser` unter dem Render-Lock; anschließend `_buffer = session.Buffer` + `Resize` auf Viewport + `BufferChanged`-Registrierung.
3. Live-Chunks laufen danach normal weiter; keine doppelten Ausgaben, da Rebuild deterministisch denselben Endzustand erzeugt.

Beteiligte Klassen/Komponenten: `TerminalControl`, `ITerminalSession`, `PseudoConsoleSession`, `TerminalReplayBuffer`, `AnsiSequenceParser`, `TerminalBuffer`, `TaskDetailView`.

### Prozessende, Fehler und Dispose-Kaskade

1. Session erkennt Prozessende (`Process.Exited` bzw. Ende des Output-Streams) → Exit-Code via `GetExitCodeProcess` auf `nativeProcessHandle` (bzw. `Process.ExitCode` beim Pipe-Pfad) → `Exited`-Event mit `TerminalSessionExitedEventArgs.ExitCode`; natives Handle wird in `Dispose` geschlossen.
2. `KiAusfuehrungsService.HandleProcessExitedAsync` (jetzt über `session.Exited` getriggert): atomares `TryRemove`, Status-Mapping (`AbsichtlichGestoppt`/`ExitCode != 0` → `Gestoppt`/`Fehler`), `DisposeSessionResourcesAsync` (`DrainOutputAsync` → `Session.Dispose` → `OutputSink.CompleteAsync`), `PersistAusfuehrungBeendetAsync`, `CliProcessStatusChanged`.
3. Fatale Laufzeitfehler der Session (Leseschleife bricht mit Exception, Pipe defekt) → `Failed`-Event → `KiAusfuehrungsService` behandelt wie Exit ohne Code → `CliProcessStatus.Fehler` + Diagnose-Log.
4. Startfehler (`PseudoConsole.Create`, `CreateProcess`, `RequiresPty`-Fehler der Factory) werfen synchron aus der Factory → `KiAusfuehrungsService` schließt den `CliOutputProtokollWriter` und meldet den Fehler (bestehendes Verhalten; Fehler landet im vorhandenen `FehlerMeldung`-Banner-Pfad).

Beteiligte Klassen/Komponenten: `PseudoConsoleSession`, `ITerminalSession`, `KiAusfuehrungsService`, `CliProcessManager` (Heartbeat/LaufStatus via `RuntimeStatusChanged`), `CliOutputProtokollWriter`.

## Änderungen an bestehenden Klassen

### `PseudoConsoleSession` (Klasse, `Infrastructure/Terminal`)

- **Implementiert:** `ITerminalSession` (statt nur `IDisposable`).
- **Neue Events:** `OutputChunk` (`EventHandler<TerminalOutputChunkEventArgs>` — pro Rohchunk vor dem Parsen), `Exited` (`EventHandler<TerminalSessionExitedEventArgs>` — bei Prozessende, Exit-Code aus `nativeProcessHandle`/`Process.ExitCode`), `Failed` (`EventHandler<TerminalSessionFailedEventArgs>` — bei fatalem Leseschleifen-/Schreibfehler).
- **Neue Eigenschaften:** `IsPseudoTerminal` (`bool` — `false` bei Pipe-Backend), `ExitCode` (`int?` — nach `Exited` belegt).
- **Neue Methoden:** `RebuildBufferFromReplay()` — `Buffer.Reset()` + Re-Parsing aller `TerminalReplayBuffer`-Chunks mit frischem `AnsiSequenceParser` unter dem neuen Render-Lock; `GetReplayChunks()` o. ä. für Diagnose/Tests.
- **Geänderte Methoden:** `Resize` — Dedupe identischer Dimensionen + Serialisierung über Lock; `ReadLoopAsync` — neue Chunk-Reihenfolge (Replay-Append → Sink → `OutputChunk`-Event → Parse → Apply unter Render-Lock → `BufferChanged`), Exit-Erkennung + `Exited`-Auslösung im Abschluss; `Dispose` — schließt zusätzlich das native Prozess-Handle.
- **Neue Konstruktorparameter:** `IntPtr nativeProcessHandle` (Default `Zero`), `TerminalSessionOptions` (Replay-Budget, `DefaultCols`/`DefaultRows`).

- **Geänderte Methode:** `Start` — Signatur von `(Guid, string effectiveWorkingDirectory, string pluginCommand, ITerminalOutputSink?)` zu `(Guid aufgabeId, TerminalSessionStartSpec spec, ITerminalOutputSink? outputSink)`; Rückgabe `TerminalSessionStartResult` statt `(Process, PseudoConsoleSession, IntPtr)`.
- **Neue Eigenschaft:** `bool IsPseudoTerminal` — kennzeichnet das Backend.

### `Win32PseudoConsoleProcessLauncher` (Klasse)

- **Neuer Konstruktorparameter:** `IOptions<TerminalSessionOptions>` — Konsument der `TerminalSessionOptions`: `PseudoConsole.Create` erhält `options.Value.DefaultCols`/`DefaultRows` statt der hartkodierten `220, 50` (`Win32PseudoConsoleProcessLauncher.cs:38`), und `CreatePseudoConsoleSession` übergibt `options.Value` an den `PseudoConsoleSession`-Konstruktor (Replay-Budget + initiale Buffer-Größe). DI-seitig kostenlos auflösbar, da der konkrete Typ registriert bleibt und `services.Configure<TerminalSessionOptions>` `IOptions` bereitstellt.

- **Geänderte Methode:** `Start` — startet `spec.FileName` + `spec.Arguments` direkt mit Pipe-Redirects statt `cmd.exe` als Hülle; `CrSubmittingInputStream` bleibt (stdin-Übersetzung `\r`→`\r\n` — weiterhin erforderlich, weil die interaktive Shell der `KiSimulatorPlugin`-Spec auf der STDIN-Pipe nur `CRLF` als Zeilenende akzeptiert); `IsPseudoTerminal = false`. ## Seiteneffekte und Risiken

- **`KiSimulatorPlugin`-Semantik ändert sich:** Von `cmd.exe /c`-One-Shot (~30-s-`ping`, selbstterminierend, stdin-taub) zu interaktiver `cmd.exe /k`-Shell (sofortige Befehlsausführung, unbegrenzte Lebensdauer). Konsequenzen: Prompts/`echo`-Marker werden sofort statt nach ~30 s ausgeführt (die erhöhten Warte-Schwellen in `E2E_SessionLimitPause` bleiben korrekt, schlagen aber schneller an); die Session endet nur noch per `exit`-Prompt oder `Kill`; Unit-Tests auf die alte Spec (`KiSimulatorPluginTests`) müssen angepasst werden.
- **E2E-/Simulationspfad:** `SimulatedPseudoConsoleProcessLauncher` startet jetzt die Spec direkt — kein 300-ms-Delay, kein injiziertes Plugin-Kommando als erste „getippte" Zeile mehr; erste Ausgabe ist das `/k`-Banner bzw. die CLI-Ausgabe. E2E-Wartebedingungen und Protokollinhalte (`CliRawExport`, Marker-Erkennung) ändern sich entsprechend.
- **`RequiresPty` im E2E-Modus:** Da der `RequiresPty`-Fehler nur bei „Preflight: PTY nicht verfügbar" greift, läuft ein `RequiresPty`-Plugin im normalen E2E-Modus weiter auf dem simulierten Pipe-Backend — bewusste Abweichung von der Produktionssemantik, damit plugin-übergreifende E2E-Szenarien (z. B. der Plugin-Wechsel zu `Softwareschmiede.Codex`) funktionieren; der harte Fehler ist per `Terminal.ForcePtyUnavailable`-Override gezielt herbeiführbar.
- **E2E-Plugin-Wechsel auf `Softwareschmiede.Codex` umgestellt:** `PluginAuswahlAbbrechenOkUndWechsel_E2E` wechselte bisher zu `ClaudeCli` — `ClaudeCliPlugin` besitzt kein `ExecutablePath`-Setting (`GetSettingGroups` nur Token + CommandLineParameters; `BuildProcessStartInfo` nutzt `_claudeExecutablePath` → Fallback `"claude"`), womit der Resolver auf Rechnern ohne Claude-Installation `NotFound` → `FehlerMeldung`-Banner produzieren würde (harter Bruch statt „läuft"), und bei `claude.cmd`-Installation die TUI auf Pipes sofort terminieren würde (`WaitForCliRunning`-Race). Gewählte Korrektur: Wechselziel `Softwareschmiede.Codex` + vorab geseedeter Credential `Softwareschmiede.Codex.ExecutablePath` = absoluter `cmd.exe`-Pfad (persistente, stdin-lesende Shell auf dem Pipe-Backend; `CodexPlugin` liest `ExecutablePath` via `ResolveExecutablePath`) + defensives Löschen von `Softwareschmiede.Codex.CommandLineParameters` — beide Keys sind bereits in `WpfTestBase.ManagedCredentialKeys` (Backup/Restore automatisch). Hinweis: Der geseedete `Softwareschmiede.Codex.ExecutablePath` (= `cmd.exe`) bleibt lifecycle-übergreifend bis zum Teardown gesetzt (Snapshot-Restore greift erst am Ende von `RunConPtyTests`) — aktuell unkritisch, da folgende Phasen den KiSimulator nutzen bzw. ein `cmd.exe`-Codex-Start sogar startfähig wäre; ein In-Phase-Cleanup wäre robuster gegen zukünftige Umstellungen (optional, kein Muss).
- **`Einstellungen_SpeichernCodexAlsStandardKiPlugin…` hinterlässt „Codex CLI" als globalen Standard:** Der finally-Block stellt nur `ExecutablePath` wieder her, nicht die Default-Plugin-Auswahl. Solange alle späteren Starts explizit `Softwareschmiede.KiSimulator` wählen, ist das unkritisch; jeder künftige Start über den Default würde jedoch auf Maschinen ohne `codex`-Installation in den `NotFound`-Pfad laufen. Geplante Härtung (betroffener E2E-Test): finally stellt zusätzlich den vorherigen Default-Plugin-Wert wieder her.
- **Breite Signaturänderung:** `PseudoConsoleSession` → `ITerminalSession` und Launcher-Signatur betreffen sämtliche Test-Doubles (`DeterministicPseudoConsoleProcessLauncher`, `FixedOutputPseudoConsoleProcessLauncher`, `OutputByTaskPseudoConsoleProcessLauncher`, `DelayedOutputPseudoConsoleProcessLauncher`), `TestPseudoConsoleSessionFactory`, `TestKiAusfuehrungsServiceFactory` sowie ViewModel-/View-Bindungen.
- **`CliSessionService`-Löschung:** risikofrei (nachweislich ohne Aufrufer/DI), verkleinert aber die „historische" Fallback-Option — dokumentierte Fallback-Rolle liegt jetzt ausschließlich beim Pipe-Backend der Factory.
- **`Exited`-Umstellung:** Exit-Erkennung wandert von `process.Exited` (Service) in die Session — Race-Bedingungen (Exit vor Event-Subscription) müssen weiter über die frühe `_handles`-Eintragung + `HasExited`-Check abgedeckt bleiben (bestehendes Muster übernehmen).
- **`.cmd`/`.bat`-Wrapping:** npm-Shims (`codex.cmd`, `devin.cmd`, …) laufen über `cmd.exe /d /s /c`. Bekannte Eigenheit: Ctrl-C gegen einen Batch-Prozess löst die cmd-Rückfrage „Batchdatei abbrechen (J/N)?" aus statt sofort zu terminieren — dokumentiertes Verhalten von Batch-Shims, kein Implementierungsfehler; der Exit-Code des Wrappers folgt dem Batch-Exit-Code. Auf dem PTY-Pfad bleibt Ctrl-C-Verhalten damit shim-abhängig (`.exe`-CLI → direktes Signal; `.cmd`-Shim → Batch-Rückfrage).
- **Executable-Formen außerhalb `.exe`/`.cmd`/`.bat`:** PATHEXT-Treffer mit anderen Erweiterungen (`.com`, `.ps1`, …) melden `NotExecutable` mit klarem Detail statt eines undurchsichtigen `CreateProcess`-Fehlers — bewusst strenger als cmd.exe (das z. B. `.ps1` über Shell-Verb ausführen könnte), weil der Direct-Start-Pfad keine Shell-Verb-Semantik hat.
- **Plugin-Health-Checks (`CheckHealthAsync`/`GetCliHelpTextAsync`)** rufen `Process.Start` mit dem unbearbeiteten Plugin-`FileName` auf und haben dieselbe `.exe`-Begrenzung — bei `.cmd`-nur-Installationen kann der Health-Check bereits heute falsch negativ ausfallen (vorbestehende Einschränkung, nicht Teil dieses Plans). Der Preflight behandelt das Health-Ergebnis als Einzelcheck; die eigentliche Startfähigkeit sichert der `TerminalExecutableResolver`-Check unabhängig davon ab. Nebenwirkung im E2E-Wechsel: Der durchgereichte `healthCheck` auf dem geseedeten `Softwareschmiede.Codex.ExecutablePath` (= `cmd.exe`) führt `cmd.exe --version` aus (`CheckHealthWithVersionCommandAsync`) — das kann bis zum internen ~10-s-Timeout laufen oder `false` liefern; beides ist ein nicht-fataler Diagnoseeintrag, verlängert aber den `PluginAuswahlAbbrechenOkUndWechsel_E2E`-Ablauf ggf. um wenige Sekunden.
- **Renderer-Erweiterung:** Alt-Screen/Scroll-Regionen verändern `TerminalBuffer`-Semantik; bestehende Snapshot-/Resize-Tests müssen weiter grün sein; die Alt-Screen-Behandlung in `TerminalControl` (Scrollback-Sperre) ist als konkrete Änderung eingeplant (siehe oben).
- **Replay bei laufender Session:** `RebuildBufferFromReplay` muss unter demselben Lock wie `parser.Parse`/`Buffer.Apply` laufen, sonst Reihenfolgeverletzung mit Live-Chunks.
- **Self-Hosting-Hinweis:** keine `Softwareschmiede.App.exe`-Prozesse beenden (CLAUDE.md).
- **`terminal-backend/` (Node-Prototyp):** bleibt unreferenziert und ist nicht Teil dieses Plans.
