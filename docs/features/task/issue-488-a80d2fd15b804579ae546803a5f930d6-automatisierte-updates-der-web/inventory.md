# Bestandsaufnahme: Automatisierte Updates der Status-Webanwendung mit msTools.Updater (Issue #488)

Analysiert wurden der Ist-Zustand des StatusServers (`server/Softwareschmiede.StatusServer`), der Desktop-Update-Stack in `src/Softwareschmiede`, die Release-Pipeline, das NuGet-Paket `msTools.Updater 0.11.0-rc.8` (XML-Doc + NuGet-Cache) sowie die Referenz-Implementierung FinanceManager (`D:\Repositories\FinanceManager\Current`) — bezogen auf die Anforderung in `requirement.md`.

## Zusammenfassung

- **msTools.Updater ist im Softwareschmiede-Repo noch nicht eingebunden:** Es gibt weder `NuGet.config`/`nuget.config`, noch ein `external/`-Verzeichnis, noch irgendeine `msTools`-Referenz in csproj/slnx. Das FinanceManager-Muster (eingechecktes `.nupkg` unter `external/msTools.Updater/` + `NuGet.config`-Feed-Quelle) ist die lokale Vorlage; im NuGet-Cache liegen Versionen bis `0.11.0-rc.8` (FinanceManager pinnt genau diese).
- **Die Bibliotheks-API ist komplett dokumentiert** (XML-Doc + README im nupkg): Ein einziger Einstiegspunkt `UseAutoUpdate(IHostApplicationBuilder, Action<AutoUpdateBuilder>)` registriert Quelle (GitHub/LocalFolder), Orchestrierung (`IAutoUpdateOrchestrator`, `IAutoUpdateCommandHandler`, `IAutoUpdateStatusProvider`), zwei Hosted Services (`AutoUpdateCheckerService` = periodische Prüfung/Download, `AutoUpdateSchedulerService` = tägliche Installation zu `ScheduledInstallTime`), Events und runtime-mutable `AutoUpdateOptions` (Singleton). `AllowPrereleaseUpdates` ist der Kanalschalter (Stable ↔ Pre-Release). Wichtig: `UseGithubSource` hat **keinen Token-Parameter** — ein Token ginge nur über `UseSource` mit selbst gebautem `AutoUpdateGithubSource` (externer `HttpClient` mit Auth-Header).
- **Installierte Version kommt aus `release-metadata.json`, nicht aus `version.json`:** Der Default-`IInstalledVersionProvider` (`ReleaseMetadataInstalledVersionProvider`) liest `release-metadata.json` aus dem Anwendungsstamm (`version`, `publishedAt`, `commitSha`, `repository`, `runtimeIdentifier`). Die Pipeline schreibt aktuell weder `version.json` noch `release-metadata.json` in die StatusServer-Pakete — **die Version wäre „unbekannt"**; die Pipeline muss `release-metadata.json` in `publish-statusserver-*` ergänzen (FinanceManager macht exakt das in `publish/<rid>/`).
- **Manifest-Format (Rezepte-Format) identisch bei Desktop und msTools.Updater:** `{ version, releaseNotes, publishedAt, assets[]: { platform, runtimeIdentifier, assetName, assetUrl, sha256, sizeBytes } }`. Achtung: `IAutoUpdatePlatformResolver.SelectPackage` wählt das Paket **nur über Plattform + RID** — ein `update.json` mit zwei `windows/win-x64`-Assets (`release.zip` + `statusserver-win-x64.zip`) wäre für den Server nicht eindeutig selektierbar; das spricht für ein **separates Server-Manifest** (per `UseGithubSource(owner, name, manifestAssetName)` adressierbar, Default `update.json`). Der Desktop-`release.zip`-Eintrag bleibt in jedem Fall unverändert.
- **Neustart ist vom Updater getragen, nicht vom Service-Manager:** Reale Deployment-Logs (Rezepte/VideoPlayer unter `D:\Repositories\…\Backup\updates\update.log`) zeigen: `systemd-run`-Transient-Unit führt `update.sh` aus → `systemctl stop <service>` → Staging/Entpacken → `cp` über App-Verzeichnis → `systemctl start` → Workspace-Bereinigung. Windows: Skript detached via WMI `Win32_Process.Create`; IIS-Erkennung automatisch (in/out-of-process, `app_offline.htm`); Windows-Dienst (`ServiceName`) oder Executable (`ExecutablePath`). `data/`- und `appsettings*.json`-Schutz geht über `AutoUpdateOptions.ProtectedFiles` (`PreserveFile`/`MergeFile`, Wildcards erlaubt — VideoPlayer-Deployment nutzt das Feature nachweislich).
- **Admin-Oberfläche ist einsatzbereit:** `AdminEndpoints` (`/admin/settings` GET + `…/session-duration` POST, `AdminOnlyPolicy` + `RequireAntiforgery`, PRG mit `?msg=`/`?err=` über `StatusMessages`), `AdminPagesComposer.RenderSettings`, `ServerSettingsService` (Key/Value-Tabelle `ServerSettings`, prozessweiter Schreiblock — neue Schlüssel brauchen **keine** Migration).
- **Desktop-Update-Stack ist fachlich vollständig, aber nicht 1:1 wiederverwendbar:** `UpdateChannel.Stable/ReleaseCandidate` deckt den geforderten Kanal ab; `UpdatePathChannelResolver` leitet den Kanal aber aus dem Desktop-Pfad „Vorabversionen"/„Produktivversionen" ab (bei msTools.Updater ist der Kanal ein einfacher bool `AllowPrereleaseUpdates`). `GitHubReleaseClient`/`UpdatePackageService`/`UpdateScriptService` implementieren eine eigene, Windows-only PowerShell-Mechanik, die msTools.Updater ersetzt. Ein `ProjectReference` von StatusServer (net11.0) auf `src/Softwareschmiede` (net11.0) ist technisch möglich, zieht aber EF-Core-Sqlite-, SignalR-Client- und Plugin-Contracts-Pakete mit.
- **TFM-Gefälle beachten:** msTools.Updater zielt `net10.0` (Abhängigkeiten `Microsoft.Extensions.* 10.0.7`), StatusServer `net11.0` — referenzierbar (net10-Bibliothek in net11-Host), die Paketversionen werden auf 11.x hochgezogen.
- **Tests:** `StatusWebApplicationFactory` (WebApplicationFactory + isolierte SQLite-Datei, `UseEnvironment(Production)`), `AuthTestClient` (Cookies/Antiforgery/PRG-Helfer), `StatusServerDbSeeder` (Scope-basierte Seed-/Assert-Helfer inkl. `AddServerSettingAsync`), `StatusServerTestDb` (In-Memory-SQLite für Unit-Tests). msTools.Updater selbst bietet Testhaken: `UseLocalFolderSource` + `DisableHostedServices()` — wichtig, weil eine `WebApplicationFactory` sonst echte Hosted Services gegen GitHub starten würde.
