# Plan: `AufgabeAusfuehrungsStatus` — Modus (regulär/autonom) von Phase trennen

Bezug: `docs/features/task/issue-205-.../continue.md`, Zeile ~92. Reine Bestandsaufnahme + Plan, **keine Implementierung** in diesem Durchgang.

## 0. Kernbefund vorab

`git show main:src/Softwareschmiede/Domain/Enums/AufgabeAusfuehrungsStatus.cs` zeigt: Auf `main` hat der Enum nur die drei Werte `NichtGestartet`/`Aktiv`/`Beendet`. Der vierte Wert `AutonomAufgabe` wurde ausschließlich auf diesem Feature-Branch eingeführt (Commit `761523a "feat: Autonome Aufgabe / Projektleiter-Modus"`) und ist **nicht gemerged**. Es existiert also keine released/produktive Installation mit Bestandsdaten `AusfuehrungsStatus = AutonomAufgabe`. Einzige Ausnahme: lokale Dev-/Self-Hosting-Datenbanken, die während der Arbeit an diesem Branch bereits eine echte Autonome Aufgabe angelegt haben (siehe CLAUDE.md Selfhosting-Hinweis) — dafür wird unten trotzdem eine defensive Datenmigration empfohlen.

Zweiter Kernbefund, der den gewählten Ansatz stark stützt: **Der Sentinel-Wert `AutonomAufgabe` überlebt in der Praxis nur sehr kurz.** `ProjektleiterAgentService.StarteAgentAsync` (Zeile 54) überschreibt `aufgabe.AusfuehrungsStatus` beim Start des Agenten sofort auf `Aktiv` — bestätigt durch `E2E_AutonomAufgabenAgentExecution.cs` Zeile 78, die nach dem Start explizit `Aktiv` (nicht `AutonomAufgabe`) erwartet. Das bedeutet: Sobald ein Unteragent existiert (was erst nach dem Agent-Start passiert), steht `AusfuehrungsStatus` in der Produktion bereits auf `Aktiv`. Der Governance-Monitoring-Filter in `UnteragentGovernanceMonitoringService.RunOnceAsync` (`... && Aufgabe.AusfuehrungsStatus == AufgabeAusfuehrungsStatus.AutonomAufgabe`) kann unter diesen Umständen **nie** einen echten laufenden Unteragenten finden — er funktioniert nur in den Unit-Tests, weil `ProjektleiterAgentServiceTestDatenFactory` den Sentinel-Wert künstlich direkt in die Test-Fixture schreibt, statt den realen Start-Flow zu durchlaufen. Das ist kein Nebenbefund, sondern ein bereits vorhandener, durch die Vermischung von Phase und Modus verursachter Bug, den der gewählte Ansatz nebenbei behebt (siehe Abschnitt 2 und Schritt 5).

## 2. Gewählter Ansatz

**`Aufgabe.AutonomKonfiguration != null` wird der alleinige Modus-Indikator.** `AufgabeAusfuehrungsStatus` wird auf die drei echten Phasenwerte (`NichtGestartet`/`Aktiv`/`Beendet`) reduziert. Eine neue Extension-Methode `IstAutonom()` auf `Aufgabe` kapselt die Prüfung.

Begründung:
- Die 1:1-Beziehung existiert bereits vollständig und wird beim Anlegen der `AutonomAufgabeKonfiguration` automatisch (EF-Relationship-Fixup über die FK `AufgabeId`, sobald beide Entities im selben `DbContext` getrackt sind) auf der `Aufgabe`-Seite nachgezogen — keine Duplikation nötig.
- Sie ist robust gegen die generischen Phasenübergänge in `AufgabeService`/`CliProcessManager`, die heute den Sentinel-Wert kaputt überschreiben (Kernbefund oben). Das behebt den bestehenden Governance-Monitoring-Bug als Nebeneffekt, nicht als Zusatzaufwand.
- Für die eine tatsächlich autonome-spezifische Unterphase, die es gibt — "Session pausiert wegen Budget-Limit" — existiert mit `AutonomAufgabeKonfiguration.SessionPauseUtc` bereits ein dediziertes, korrekt separates Feld (aus dem letzten abgeschlossenen Batch). Ein zusätzliches `AutonomAufgabeStatus`-Enum hätte hier keinen Mehrwert, sondern würde denselben Fehler (zwei Wahrheitsquellen für denselben Zustand) wiederholen.

**Geprüfte und verworfene Alternative:** Eigenes `AutonomAufgabeStatus`-Enum auf `AutonomAufgabeKonfiguration` (z. B. `Initialisiert`/`Laeuft`/`Pausiert`/`Abgeschlossen`). Verworfen, weil sich beim Durchgehen aller Fundstellen kein einziger Fall zeigt, der einen eigenen autonomen Phasenraum bräuchte, der nicht schon durch `AusfuehrungsStatus` (Phase, geteilt mit regulären Aufgaben) + `SessionPauseUtc` (Pause-Flag) abgedeckt ist. Ein Zusatz-Enum würde nur mehr Zustandsraum ohne zusätzlichen Informationsgehalt schaffen und wäre selbst wieder ein Kandidat für künftige Inkonsistenzen (z. B. müsste es bei jedem `AusfuehrungsStatus`-Phasenübergang mitgepflegt werden).

   ```csharp

Das ist der wichtigste Stolperstein dieses Refactorings; jede Umstellung eines Call-Sites muss diesen Punkt einzeln prüfen (siehe Schritte 4–6).

## 4. Risiken / offene Fragen

1. **Schritt 10 (TaskDetailViewModel-Fix) ist eine echte Verhaltensänderung, nicht nur Refactoring.** Er behebt eine Lücke, die schon heute (unabhängig von diesem Enum-Split) besteht, sobald ein Projektleiter-Agent läuft. Empfehlung: trotzdem im selben Umsetzungsschritt mit beheben, weil er exakt dieselben Call-Sites (`SollCliAnzeigen`/`DarfAusfuehrungStarten`-Aufrufer) berührt, die durch den Split ohnehin angefasst werden, und weil ein Nutzer sonst nach diesem Refactoring in der `TaskDetailView` eine funktionslose/verwirrende reguläre CLI-Leiste für eine laufende Autonome Aufgabe sehen könnte. Falls der Product Owner das lieber als eigenes Ticket getrennt sehen will, ist Schritt 10 der einzige, der ohne Verlust der übrigen Konsistenz weggelassen werden kann — alle anderen Schritte hängen nicht von ihm ab.
2. **Fixup-Abhängigkeit (Schritt 1).** `IstAutonom()`/`AutonomKonfiguration != null` liefert nur dann korrekt, wenn die Navigation Property geladen ist. Jede Umstellungsstelle wurde oben einzeln auf diese Voraussetzung geprüft (`SessionManagementService`, `ProjektleiterAgentService` laden bereits per `.Include`; `AufgabeRecoveryService` muss es neu ergänzen; `TaskDetailViewModel` muss geprüft werden). Ein künftiger Aufrufer, der das übersieht, bekommt keinen Compile-Fehler, sondern ein stilles `false` — Empfehlung an den Implementierungs-Agenten, in den XML-Doc-Kommentar von `IstAutonom()` einen expliziten Warnhinweis zu schreiben.
3. **Datenmigration (Schritt 11) ist eine Vorsichtsmaßnahme, kein bestätigter Bedarf.** Es wurde nicht geprüft, ob im aktuell laufenden Self-Hosting-Prozess (der laut CLAUDE.md ggf. diese Session selbst hostet) tatsächlich bereits eine Autonome Aufgabe mit Status `AutonomAufgabe` in der lokalen SQLite-DB liegt — das explizit zu prüfen hätte bedeutet, in die laufende App-Instanz einzugreifen, was außerhalb des Auftrags "nur Bestandsaufnahme + Plan" liegt und laut CLAUDE.md ohnehin nicht ohne Rücksprache mit build-relevanten Risiken verbunden werden soll. Die Migration ist so oder so ungefährlich (No-Op, falls keine solche Zeile existiert) und wird uneingeschränkt empfohlen.
4. **Governance-Monitoring-Bugfix (Schritt 4) ändert Produktionsverhalten**, nicht nur Testverhalten: Der Governance-Loop wird nach diesem Fix erstmals tatsächlich aktive Unteragenten finden und ggf. Token-/Laufzeit-Limits durchsetzen (Abbruch via `UnteragentAbbruchException`), was er zuvor faktisch nie tat. Das ist im Sinne der Anforderung eindeutig erwünscht (das Feature soll ja funktionieren), aber ein Implementierungs-Agent sollte sich bewusst sein, dass das kein reines Rename/Refactoring ist, sondern die erste funktionierende Aktivierung dieses Sicherheitsmechanismus — entsprechend sorgfältig sollten die neuen/angepassten Tests in Schritt 5 sein.
