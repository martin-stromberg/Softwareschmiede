# Requirement: GitHub-Notifications als Eingangskanal für SCM-Ereignisse (Kontomodus)

## Fachliche Zusammenfassung

Die bestehende SCM-Ereignisüberwachung (`ScmEventMonitoringService`) erhält einen umschaltbaren **Kontomodus** mit zwei Betriebsarten:

1. **Benutzerkonto (bisheriges Verhalten):** Der `ScmEventMonitoringService` pollt repository-weit alle Referenzen der aktivierten Projekt-Repositories über `IScmEventSource` und akzeptiert nur Texte mit dem konfigurierten Trigger-Keyword (`scm.trigger.keyword`, Standard `$Softwareschmiede`) vom authentifizierten Repository-Owner.
2. **Separates Konto (neu):** Die Anwendung arbeitet über ein eigenes GitHub-Konto (z. B. `@softwarewerkstatt`). Eine Aufgabe wird zur Bearbeitung zugewiesen, indem dieses Konto per `@mention` in einer Issue-/PR-Beschreibung oder einem Kommentar genannt wird. Dadurch entsteht in der GitHub-Notifications-Inbox des separaten Kontos ein Eintrag. Statt Repositories zu scannen, wird ausschließlich diese Inbox überwacht; aus den Notification-Einträgen ergeben sich Repository und Issue/Pull Request, für die der bestehende Ereignis- und Dispatch-Pfad gestartet wird.

Fachliche Schutzregel (unverändert, jetzt als Filter auf den Notification-Eingang): Es dürfen nur Aufgaben für Repositories bearbeitet werden, die als `GitRepository` an einem Projekt erfasst und aktiviert sind — Notifications zu fremden Repositories werden nicht verarbeitet.

## Betroffene Klassen und Komponenten

- `ScmEventMonitoringService` (`src/Softwareschmiede/Application/Services/`): zweiter Akquisitionspfad — im Kontomodus „Separates Konto" Inbox-Polling statt `EnumerateReferencesAsync`-Repository-Enumeration; die anschließende Verarbeitung (Accept, Validierung, Dispatch) soll möglichst unverändert über `ScmEventStore.AcceptBatchAsync` → `ScmEventOrchestrator` laufen.
- `GitHubPlugin` (`plugins/Softwareschmiede.Plugin.GitHub/`): neue Lesefähigkeit für die GitHub-Notifications-Inbox (`gh api notifications` bzw. `GET /notifications`, `reason: mention`); Auflösung Notification-Thread → `ScmEventReference` (Repository, `ScmReferenceKind`, Nummer). Vermutlich Erweiterung von `GitHubPlugin.Events.cs` und `IGitHubEventApiClient`.
- `Softwareschmiede.Plugin.Contracts` (`src/Softwareschmiede.Plugin.Contracts/Domain/`): neue oder erweiterte Fähigkeit, z. B. ein optionales Interface `IScmNotificationSource` neben `IScmEventSource` sowie Value Objects für Notification-Einträge (Thread-ID, Subject, Repository, `updated_at`, Reason).
- `AppEinstellungService` (`src/Softwareschmiede/Application/Services/`): neuer Einstellungsschlüssel für den Kontomodus (z. B. `scm.monitoring.accountmode`), analog zum `ScmBackmergeModus`-Muster (`ScmBackmergeModeKey`, `Get-/SetScmBackmergeModusAsync`).
- Domain-Enum (`src/Softwareschmiede/Domain/Enums/`): neuer Enum für den Kontomodus (z. B. `Benutzerkonto` / `SeparatesKonto`), analog `ScmBackmergeModus`.
- `ScmEventValidationService`: anzupassen bzw. modusabhängig — die Regel „authentifizierter Nutzer = Repository-Owner" (`ScmEventRepository.ViewerId`/`OwnerId`) und die Trigger-Keyword-Pflicht greifen im separaten-Konto-Modus nicht unverändert (der Viewer ist dann das Bot-Konto, nicht der Owner).
- Authentifizierung: zweites Credential im `ICredentialStore` (PAT des separaten Kontos; bisheriger Schlüssel `Softwareschmiede.GitHub.Token` im `GitHubPlugin`); zusätzliches `PluginSettingField` (Secret) in `GitHubPlugin.GetSettingGroups()` oder vergleichbare Konfiguration — siehe Offene Fragen.
- `SettingsViewModel` / Settings-View (`src/Softwareschmiede.App/`): Auswahl des Kontomodus unter **Einstellungen → Allgemein → SCM-Ereignisse**; ggf. Pflichtfeld-Validierung (Token des separaten Kontos erforderlich, wenn Modus aktiv).
- `IScmAgentAccess.GetAgentEnvironmentAsync` / `KiAusfuehrungsService`: zu klären, welches Token die CLI-Agenten-Sitzung (`GH_TOKEN`, git-`http.extraheader`) im separaten-Konto-Modus erhält.
- Tests: `AppEinstellungService`-Tests, `ScmEventValidationService`-Tests, `ScmEventMonitoringService`-Integrationstests mit gemocktem `IScmEventSource`/Notification-Feed (`ScmDispatchFixture`), `SettingsViewModelTests`; E2E nur falls das View-Pattern neue Settings-Marker erfordert.

## Implementierungsansatz

- Konfiguration wird wie die übrigen SCM-Ereignis-Schalter pro Poll-Zyklus gelesen (vgl. `ScmMonitoringEnabledKey` in `ScmEventMonitoringService.RunOnceAsync`), sodass der Modus ohne Neustart wirkt.
- Erweiterungspunkt: Der Notification-Eingang liefert Referenzen statt Textstände. Naheliegend ist, die gefundene `ScmEventReference` danach in den bestehenden `ReadEventsAsync`-Pfad einzuspeisen (Beschreibung, Kommentare, Review-Kommentare, Reviews lesen) und dort den auslösenden Text (mit dem `@mention`) dem bisherigen Snapshot-/Deduplizierungs-Mechanismus (`ScmContentSnapshot`, `ScmObservationCheckpoint`, `EventKey`) zuzuführen. Checkpoints brauchen einen neuen `SourceKey`-Namensraum (z. B. `notifications/{provider}/{account}`). — Annahme: Der konkrete Textinhalt bleibt Eingang des Orchestrators; die Notification ersetzt nur die Referenz-Ermittlung.
- Die Projektbeschränkung kann an derselben Stelle greifen wie heute: Auflösung der Notification-Repository-Identität gegen die Liste aktiver `GitRepository`-Einträge (kanonische Identität über `GetEventRepositoryAsync`); nicht registrierte Repositories werden verworfen.
- Abhängigkeiten: Der Dispatch-Pfad (`ScmEventOrchestrator`, `ScmEventOutbox`, `IScmEventResponder`, `ScmEventTaskResolver`, Aufgabenanlage, CLI-Start) sollte wiederverwendet werden; neue Logik beschränkt sich auf Akquisition, Authentifizierung des zweiten Kontos und modusabhängige Validierung.
- Sicherheit: Das Bot-Token folgt denselben Regeln wie das bestehende Token (nur `GH_TOKEN`-Umgebungsvariable, `SanitizeSensitiveOutput`, kein Token in Prompts/Logs/Persistenz).

## Konfiguration

- Ebene: Anwendungseinstellungen (global, Key-Value über `AppEinstellungService`), GUI unter **Einstellungen → Allgemein → SCM-Ereignisse** — dort liegen bereits `scm.monitoring.enabled`, `scm.trigger.keyword`, `scm.taskcompletion.*`, `scm.backmerge.mode` und `scm.prompt.append.*`.
- Vorschlag: Enum-Einstellung `scm.monitoring.accountmode` (`0` = Benutzerkonto, `1` = SeparatesKonto; Standard `0`, damit Bestandsverhalten erhalten bleibt).
- Secret-Ebene: PAT des separaten Kontos als zweiter Eintrag im `ICredentialStore` (eigener Credential-Key, z. B. `Softwareschmiede.GitHub.AgentToken`), konfiguriert über die Plugin-Einstellungen des GitHub-Plugins (zusätzliches `PluginSettingField` vom Typ `Secret` in der Gruppe „Authentifizierung").

## Nachträglich ergänzte Anforderung: Umstellung der SCM-Überwachung auf prozesslosen HTTP-Transport

**Befund (verifiziert):** Die SCM-Überwachung startet über `CliRunner` sehr häufig `gh.exe`-Konsolenprozesse (gemessen ~150/Minute, ~73.000/Tag). Obwohl `CreateNoWindow=true` gesetzt ist, erzeugt Windows 11 pro gestartetem Konsolenprozess einen `conhost.exe`-Kindprozess, der kurz ein sichtbares Konsolenfenster aufblitzen lässt — empirisch bestätigt: bei deaktivierter Überwachung tritt das Problem nicht mehr auf.

**Anforderung:** Die GitHub-API-Aufrufe der Überwachung (und idealerweise sämtlicher periodischer GitHub-API-Pfade) sollen nicht mehr über `gh`-Kindprozesse laufen, sondern über direkte HTTP-Aufrufe (z. B. `HttpClient`) mit dem PAT aus dem `ICredentialStore`. Der existierende `IGitHubEventApiClient`-Vertrag (`GitHubEventApiRequest(Host, Method, Endpoint, JsonBody)` → `GitHubEventApiResponse(StatusCode, Body, Headers)`) soll dabei möglichst erhalten bleiben, damit die Plugin-Logik unverändert weiterarbeitet — inkl. Response-Headern für Pagination/Backoff (`Link`, `X-RateLimit-*`, `Retry-After` — bisher via `gh api --include` gewonnen). Zu klären u. a.: Base-URL-Mapping (`github.com` → `https://api.github.com`, Enterprise-Hosts → `https://{host}/api/v3`), Pflicht-Header (`Accept`, `X-GitHub-Api-Version`, `User-Agent`, `Authorization: Bearer`), Ersatz für `gh auth status` (z. B. `GET /user`), Behandlung der bisher direkt über `CliRunner` laufenden `gh api`-Calls in `GitHubPlugin.cs` (Zeilen ~380–1486: code-scanning/alerts, pulls, git/trees, graphql etc. — mindestens alle periodisch genutzten Pfade prozesslos stellen), und ob `gh` danach noch Produktivvoraussetzung ist oder nur noch für manuelle/userinitiierte Pfade. Der geplante zweite `IGitHubEventApiClient` für das Agent-Konto (SeparatesKonto-Modus) wird ebenfalls HTTP-basiert — beide Clients teilen die HTTP-Implementierung, unterscheiden sich nur im Token (Credential-Keys `Softwareschmiede.GitHub.Token` vs. `Softwareschmiede.GitHub.AgentToken`). `git`-CLI für lokale Repository-Operationen bleibt unverändert (selten, kein API-Pfad).

**Token-Schutz (verbindlich):** Der PAT/das AgentToken darf niemals kompromittiert werden — nicht in Logs, nicht in Exception-Messages, nicht in Request-URLs (kein `?access_token=` o. ä.), nicht in Test-Artefakten, nicht in Planungs-/Review-Dokumenten. Token fließt ausschließlich `ICredentialStore` → `Authorization`-Header des `HttpClient`. Logging darf niemals Request-Header dumpen; `SanitizeSensitiveOutput` muss beide Token-Werte maskieren. Tests nur mit Fake-Tokens.

## Offene Fragen

1. **Authentifizierung des separaten Kontos:** Reicht ein zweiter Personal Access Token in den GitHub-Plugin-Einstellungen, oder soll `gh auth` mit Mehrfachkonten genutzt werden? Welche Token-Scopes werden benötigt (mindestens `notifications`; fürs Lesen der Referenzinhalte und Ausführen von Antworten vermutlich `repo`)?
2. **Repository-Zugriff des Bot-Kontos:** Muss `@softwarewerkstatt` als Collaborator/Leser auf den Projekt-Repositories eingeladen sein, damit Notification-Subject-Inhalte gelesen und Antworten (👀-Reaktion, Kommentare) ausgeführt werden können? Kann derselbe `CanWrite`-Check (`ScmEventRepository.CanWrite`) pro Repository gelten?
3. **Welches Token wirkt wo?** Im separaten Modus: Lesen der Inbox eindeutig mit dem Bot-Token — aber welchen Token bekommen a) die Host-Antwortaktionen (`IScmEventResponder`, Empfangsreaktion/Kommentare) und b) die CLI-Agenten-Sitzung (`IScmAgentAccess.GetAgentEnvironmentAsync` → `GH_TOKEN`)? Antworten als Bot-Account oder weiterhin als Benutzer?
4. **Trigger-Keyword im separaten Modus:** Ersetzt die `@mention` das Trigger-Keyword vollständig, oder muss der genannte Text zusätzlich `scm.trigger.keyword` enthalten? Ist eine Mention im PR-/Issue-Body (Beschreibung) gleichwertig mit einer Mention im Kommentar?
5. **Berechtigung zum Zuweisen:** Darf jeder GitHub-Nutzer durch eine Mention des Bot-Kontos eine Aufgabe auslösen, oder gilt weiterhin eine Einschränkung (z. B. nur Repository-Owner/-Collaborator als Mention-Autor)? Die bisherige Owner-Regel (`ViewerId` == `OwnerId` in `ScmEventValidationService.GetRejection`) kann im Bot-Modus so nicht gelten.
6. **Notification-Typen:** Nur `reason = mention` berücksichtigen oder auch andere Reasons (z. B. `assign`, `subscribed`)? Sollen verarbeitete Notifications via API als gelesen markiert/„done" gesetzt werden oder bleibt Deduplizierung ausschließlich lokal über Checkpoints/Snapshots?
7. **Nicht-Projekt-Repositories:** Notifications zu Repositories ohne registriertes, aktiviertes Projekt — still verwerfen, als Diagnose/Log sichtbar machen oder als wartenden Eintrag in der SCM-Ereignisübersicht führen?
8. **Umschalten des Modus:** Was passiert mit bereits in der Inbox liegenden Ereignissen und Checkpoints beim Wechsel zwischen Benutzer- und Bot-Modus (Parallelbetrieb beider Pfade oder exklusiv)?
9. **Andere SCM-Provider:** Gilt der neue Modus ausschließlich für GitHub (Bitbucket/Local Directory implementieren ohnehin keine `IScmEventSource`)? Bestätigung erwünscht.
