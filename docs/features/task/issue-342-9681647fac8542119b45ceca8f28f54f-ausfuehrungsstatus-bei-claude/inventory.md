# Bestandsaufnahme: Ausführungsstatus bei Claude — Synchronisation Aufgaben-Fußzeile ↔ Aufgabenliste

Bestandsaufnahme zur Anforderung aus `requirement.md` (Issue #342): Die Fußzeile der Aufgabendetailansicht zeigt „CLI-Status: Ausführung läuft" (Live-Zustand der `ITerminalSession`), während die Aufgabenkachel in der aktiven Aufgabenliste „✓ Bereit" anzeigt (persistierte Laufdaten der `Aufgabe`). Analysiert wurden die beiden Statusprojektionsketten (Persistenz-Brücke `CliProcessManager`, Event-Quelle `KiAusfuehrungsService`, Laufdaten-API `AufgabeService`, Klassifikation `KiAusfuehrungsStatusKlassifikation`, UI-Aktualisierung `MainWindowViewModel`/`TaskDetailViewModel`) sowie der Ausgangszustand der projektweiten Tests.

## Zusammenfassung

- **Zwei getrennte Statusketten existieren und sind etabliert:** Die Fußzeile bindet sich direkt an die live `ITerminalSession` (`TaskDetailViewModel.AttachCliStatusSession` → `RuntimeStatusChanged` → `CliStatusText`); die Kachel wird ausschließlich aus persistierten Feldern der `Aufgabe` befüllt (`AktiveRunId`, `LastHeartbeatUtc`, `LaufStatus`, `AusfuehrungsStatus`, `Status` → `KiAusfuehrungsStatusKlassifikation.Klassifiziere`). Es existiert **kein** Rückkanal, der den Live-Sitzungszustand in die Kachel-Klassifikation einfließen lässt.
- **Der einzige Persistenz-Setzpfad für `AktiveRunId` läuft über das `CliProcessStatus.Gestartet`-Ereignis** (`CliProcessManager.OnCliProcessStatusChanged` → `AufgabeService.AktivenLaufSetzenAsync`, fire-and-forget). Alle identifizierten Early-Return-/Wiederverwendungspfade, die eine laufende Session zurückliefern, feuern dieses Ereignis **nicht** (`KiAusfuehrungsService.StartCliCoreAsync` Z. 129–139, `StartTerminalSessionCoreAsync` Z. 224–235, `EntwicklungsprozessService.CliNeustartenCoordinatedAsync` Z. 263–268).
- **Alle fünf Divergenz-Hypothesen der Anforderung sind im Code verifiziert** (Details: [Divergenzanalyse](inventory/divergenzanalyse.md)). Ergänzend gefunden: `TaskDetailViewModel.CliStoppenAsync` (Z. 910–933) ruft `AktivenLaufBeendenAsync` auch dann auf, wenn `StopCliAsync` den Prozess nicht beenden konnte (Fehler werden dort nur geloggt, `KiAusfuehrungsService.cs` Z. 474–477) — Laufdaten gelöscht, Prozess und Fußzeilen-Session leben weiter.
- **Selbstheilung ist strukturell ausgeschlossen:** `AufgabeService.AktualisiereLaufStatusAsync` ist No-Op bei `AktiveRunId == null` (Z. 1037–1038); `SubscribeRuntimeStatus` läuft nur über das `Gestartet`-Ereignis; `AufgabeLaufAktivitaet.IstAktiv` verlangt zwingend `AktiveRunId != null`. Ein einmal fehlgeschlagener/ausgebliebener `AktivenLaufSetzenAsync`-Aufruf kann durch spätere `RuntimeStatusChanged`-Ereignisse oder Heartbeat-Ticks nicht repariert werden.
- **Fehler werden konsequent nur geloggt:** `CliProcessManager.ExecuteWithAufgabeServiceAsync` (Z. 256–284) schluckt alle Exceptions der Laufdaten-Persistierung (Warnung). Bei Fehlschlag feuert zusätzlich kein `LaufdatenChanged` (Z. 266) — die Kachel erhält nicht einmal einen Refresh-Anstoß.
- **`AufgabeService.StartenAsync` persistiert den problematische Zwischenzustand absichtlich:** `AusfuehrungsStatus = Aktiv` bei `AktiveRunId = null` (Z. 775–781). `TaskDetailViewModel.StartCliAndUpdateStateAsync` persistiert bei erfolgreicher (ggf. wiederverwendeter) Session ebenfalls nur `AusfuehrungsStatus = Aktiv` via `AusfuehrungAktivSetzenAsync` (Z. 1712), niemals `AktiveRunId`.

Test-Ausgangszustand: **0 Fehlschläge** in allen ausgeführten Lanes — stabile Lane `Softwareschmiede.Tests` 2200/2201 bestanden (1 beabsichtigt übersprungen), `Softwareschmiede.IntegrationTests` 257/257, OsInterface-Lane `Softwareschmiede.Tests` 51 bestanden/19 umgebungsbedingt übersprungen (WPF-E2E und ConPTY via `SOFTWARESCHMIEDE_SKIP_WPF_E2E_TESTS=1` bzw. `SOFTWARESCHMIEDE_SKIP_CONPTY_TESTS=1`), OsInterface `IntegrationTests` 9/9. Nachweis: [Tests](inventory/tests.md).
