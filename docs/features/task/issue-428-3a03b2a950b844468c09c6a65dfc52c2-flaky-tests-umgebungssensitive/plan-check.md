## Hinweise

- **`Flaky`-Vergabe vs. eigene Vergaberegel:** Der Plan dokumentiert die Regel „`Flaky` nur bei dokumentiertem Flake-Ereignis oder Analyzer-Befund", markiert aber alle drei RestrictedProcess-Methoden mit `Flaky`. Dokumentiert ist nur der PR-#427-Flake von `RestrictedWindowsProcess_ReadsWritesAndCompletesChannel_ButCannotWriteAppData`; `…_WithoutDedicatedCapability_DeniesChannel` und `RestrictingSid_RejectsAccountsAndBroadPrincipals` haben kein dokumentiertes Flake-Ereignis — letztere startet nicht einmal einen Prozess (nur `WindowsIdentity.GetCurrent()` + `ValidateRestrictingSid`). Da `Flaky` hier ohnehin nur innerhalb der best-effort-Lane retry-berechtigt, ist die Auswirkung gering; konsistent wäre entweder nur den dokumentierten Flake-Kandidaten zu markieren oder die Regel um „gleiche OS-nahe Mechanik derselben Testdatei" zu erweitern.
- **Step-Scheduling im `os-interface tests`-Job:** Schlägt `Test OS interface (Softwareschmiede.Tests)` fehl, wird `Test OS interface (IntegrationTests)` durch das implizite `if: success()` der GitHub-Actions-Steps übersprungen — der Integration-Testlauf fehlt dann komplett (bestehendes Workflow-Verhalten, nicht planinduziert). Der Retry-Schritt (`if: failure()`) läuft trotzdem; für das Integrationsprojekt existiert dann kein Primär-TRX, und das Skript meldet per Spezifikation „keine Flaky-Fehlschläge" mit Exit 0 — Verhalten konsistent, aber im Job-Log als Einschränkung sichtbar.
- **VSTest-Filter im Retry:** `--filter "(Category=Flaky)&(FullyQualifiedName~name1|FullyQualifiedName~name2)"` ist gültige VSTest-Syntax (Klammergruppierung + `|`/`&` unterstützt); die Anführungszeichen sind im `pwsh`-Kontext zwingend (`|` wäre sonst Pipeline-Operator) — im Plan korrekt gesetzt. Der Filter `Category=Flaky` ist auswertbar, da `[Trait("Category", "Flaky")]` einen zweiten `Category`-Wert setzt; Koexistenz zweier `Category`-Traits auf einer Methode ist im Repo bereits belegt (`CliEmbeddingServiceIntegrationTests.cs` Z. 64–65: `[OsInterfaceFact]` + `[Trait("Category","ConPTY")]`).
- **`FlakyConventionTests` deckt nur `Softwareschmiede.Tests` ab:** Das Integrationsprojekt hat keine Assembly-Referenz auf `Softwareschmiede.Tests`; die Konvention greift dort nur über Doku + Review. Vom Plan transparent benannt (Validierungsregeln) — akzeptabel, aber als Restrisiko bewusst halten.
- **`--no-build` im Retry-Schritt:** Konsistent mit den bestehenden CI-Schritten (Build läuft vorher im selben Job); die Projektregel „Never use --no-build" betrifft lokale Diagnose-/Testläufe in dieser Sandbox, nicht den CI-Re-Run nach erfolgtem Build — kein Konflikt.
- **`tasks.md`-Konvention:** Der Plan referenziert kein `tasks.md`; die Repo-Konvention in `docs/features/` ist `todo.md` (alle bestehenden Feature-Verzeichnisse). Kein Konflikt.
- **Doc-Drift bestätigt:** `docs/help/stabilitaet/os-interface-tests.md` (Z. 45–51) referenziert den nicht mehr existierenden Workflow `test.yml` und veraltete Schrittnamen — der geplante Aktualisierungsschritt ist korrekt erfasst.
- **`gh run rerun --job`:** Korrekte gh-Syntax; benötigt die numerische Job-Datenbank-ID (aus `gh run view --job <id>` bzw. `--json jobs`) — bei der Doku des Abschnitts kurz mit aufnehmen.
