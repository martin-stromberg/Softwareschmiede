# Release Notes

## Important Notes Before Update

- GitHub and Bitbucket plugins no longer use SSH for git operations: SSH remote URLs (`git@…`, `ssh://…`) are automatically converted to HTTPS, and the previously written insecure SSH configuration (`GIT_SSH_COMMAND` environment variable / `core.sshCommand` git config with disabled host key checking) is removed. Repositories that are only reachable via SSH can no longer be used through the plugins.
- Plugin loading is restricted to a hard-coded whitelist of the shipped first-party plugin assemblies: a DLL in `plugins/` is only loaded if both its file name and its real assembly name (read from metadata) match the whitelist — foreign or self-added plugin DLLs are skipped and logged as a warning. In plugin subfolders, only the entry DLL matching the folder name is a load candidate.

## What's New

- Terminal SCM event statuses no longer block a task permanently: the completion monitoring and the per-task event queue now follow a binding allowlist — only the final statuses `Verarbeitet` and `Abgebrochen` plus the terminal clarification statuses `VerarbeitungUngeklärt` and `ZustellungUngewiss` let processing continue, while every transient or unknown status still blocks conservatively. A task's automatic completion is therefore no longer stuck forever behind an event that can only be clarified manually, and queued follow-up events of the same task are delivered as soon as their predecessor reaches a final or terminal state. In addition, a `pullRequestNumber` reported in `complete.json` is now registered as a `PullRequestReference` even when the event ends uncleanly — independent of `accepted.json`, of a failed completion batch check, or of a missing acceptance message — deduplicated per task.
- The application runtime is now .NET 11: the app, the domain library, all first-party plugins and the CI/release toolchain have moved from `net10.0` to `net11.0`, bundled with the EF Core 11 / Microsoft.Extensions 11 package line, SQLitePCLRaw 3.x and the xunit.v3 test toolchain; redundant `Microsoft.Extensions.*` references now provided by the runtime were removed.
- Newly created issues can now be prepared automatically (issue preparation, opt-in under Settings → Automation → Issue-Aufbereitung via the global switch plus a per-repository selection): after a one-time baseline that never scans existing issues retroactively, a newly created issue produces exactly one internal preparation job — a purpose-marked task plus a trigger-free event visible in the SCM event queue as "Issue-Aufbereitung" that is immediately due; self-written description updates cannot retrigger it, and trigger events on the same issue still resolve to the regular task. The job runs a fixed analysis prompt (title and body — understandability, completeness, missing information, open questions, technical and domain risks, conflicting goals, alternatives, possible misinterpretations) on the configured preparation plugin (with the same fallback chain as SCM events), counts toward the global and per-plugin execution limits, then replaces the issue body remotely via the outbox — the title is never changed — and optionally documents weaknesses, open questions, approaches, risks and conflicts as an issue comment (switch `scm.issueaufbereitung.comment.enabled`, default on). If no runnable plugin is available nothing starts and the job waits with an honest reason; failures are only logged and recorded in the task protocol — the issue stays untouched and no error comment is ever created.
- SCM event execution slots are now refilled immediately: when a CLI execution ends or a task is paused/unpaused, the same prioritized start check as the regular poll runs instantly — queued SCM events start without waiting for the next 60-second cycle, still serialized under the existing task leases and atomic slot limits, with the poll remaining as a slower safety net.
- Parallel AI CLI executions from SCM events are now configurable: a global limit (Settings → Automation → Run tasks → "Maximale parallele Ausführungen") plus an optional per-AI-plugin limit (Settings → Plugins → `<plugin>` → "Ausführungsbegrenzung"), each an integer ≥ 1 or empty for unlimited — the stricter of the two applies. When a limit is reached the event stays in the queue with an honest waiting reason and a protocol entry and starts automatically once a slot frees up; running executions are never interrupted, and continuations of active tasks are dispatched before due delayed events before regular input order.
- The SCM response channel can now update an issue's description: a persistent outbox action with a deterministic action ID writes the new body via `PATCH` on the issue (the title is left untouched), the marker-based reconcile prevents duplicate writes even across restarts, and failures are typed (authentication/permission failures block honestly until retried via "Erneut prüfen", rate limits and temporary failures retry automatically with backoff).
- SCM-triggered runs now select their AI plugin robustly: a stored assignment (task, project, or global default) pointing to a disabled, uninstalled, or unloadable plugin is skipped in favor of the next configured default; if no configured stage yields a runnable plugin, the event stays in the queue with an understandable waiting reason (naming the skipped assignments) and a protocol entry instead of being silently discarded or permanently locked — it starts automatically after the configuration is corrected, while an explicit CLI choice in the event queue remains strict with no silent fallback.
- Screenshot evidence from CLI SCM event runs is now published host-side: agents place evidence images in the `attachmentsPath` directory provided in the private response channel (they must not upload them themselves), the app validates the files (png, jpg, jpeg, gif, webp; up to 10 MiB each; up to 16 files) and embeds them as attachments in a GitHub comment — files that fail validation appear in the same comment with a per-file skip reason; failed or pending publications stay visible as integration hints in the SCM event queue and can be retried via "Erneut prüfen".
- New public project website via GitHub Pages: the repository now ships a static landing page (`site/`, deployed from `main` to `https://martin-stromberg.github.io/Softwareschmiede/`) presenting the application — purpose, key features, screenshots, and links to releases, repository, and documentation — with responsive light/dark styling matching the app themes.
- SCM event tasks can request a delayed execution: writing the configurable delay keyword (default `#verzögert`, Settings → Automation → Run tasks) followed by a duration such as `30min`, `4h`, `2t`, `1w` or `m1` (calendar day of month) in the same text as the trigger defers the event — the event stays in the queue as "Verzögert", the task is paused until the target time, the receipt is commented on GitHub, the persisted timer survives restarts and blocks the automatic shutdown (maximum 32 days).
- GitHub Enterprise: HTTPS git operations now authenticate against GitHub Enterprise hosts — the `http.extraheader` key is bound per operation to the host of the actually contacted remote URL instead of being hard-wired to `github.com`; PR checkouts from forks bind the fetch target to the fork's source repository.
- SCM event monitoring now also accepts the GitHub `github-actions` account (`github-actions[bot]` / `app/github-actions`) as a trusted author/editor in addition to the repository owner — issues and comments containing a trigger that were created by GitHub Actions workflows are executed as tasks automatically.
- Security: downloaded update packages are now verified against the SHA-256 hash published in the update manifest (`update.json`) before being installed — a tampered or corrupted download is discarded instead of applied. The update progress dialog shows a new "Verification" phase.
- Security: the GitHub and Bitbucket plugins now use HTTPS-only git transport — the insecure SSH configuration with disabled host key verification (a man-in-the-middle attack vector) has been removed. Existing managed working copies are migrated automatically: on the next push, pull, or PR checkout the remote URL is switched to HTTPS and the plugin-written `core.sshCommand` entry is unset.

## Wichtige Hinweise vor dem Update

- Die GitHub- und Bitbucket-Plugins verwenden für Git-Operationen kein SSH mehr: SSH-Remote-URLs (`git@…`, `ssh://…`) werden automatisch auf HTTPS umgestellt, und die zuvor geschriebene unsichere SSH-Konfiguration (`GIT_SSH_COMMAND`-Umgebungsvariable / `core.sshCommand`-Git-Konfiguration mit deaktivierter Host-Key-Prüfung) wird entfernt. Repositories, die nur über SSH erreichbar sind, können über die Plugins nicht mehr genutzt werden.
- Das Laden von Plugins ist auf eine fest kodierte Whitelist der mitgelieferten First-Party-Plugin-Assemblies beschränkt: Eine DLL in `plugins/` wird nur geladen, wenn sowohl ihr Dateiname als auch ihr echter Assembly-Name (aus den Metadaten gelesen) auf der Whitelist stehen — fremde oder selbst hinzugefügte Plugin-DLLs werden übersprungen und als Warnung protokolliert. In Plugin-Unterordnern ist nur noch die zum Ordnernamen passende Entry-DLL ein Ladekandidat.

## Neuerungen

- Terminale SCM-Ereignis-Stati blockieren eine Aufgabe nicht mehr dauerhaft: Abschlussüberwachung und aufgabenbezogene Ereignis-Warteschlange folgen jetzt einer verbindlichen Freigabeliste — nur die finalen Stati `Verarbeitet` und `Abgebrochen` sowie die terminalen Klärungsstati `VerarbeitungUngeklärt` und `ZustellungUngewiss` geben weiter, während jeder transiente oder unbekannte Status weiterhin konservativ blockiert. Der automatische Abschluss einer Aufgabe bleibt daher nicht mehr dauerhaft hinter einem nur manuell klärbaren Ereignis hängen, und wartende Folgeereignisse derselben Aufgabe werden zugestellt, sobald ihr Vorgänger einen finalen oder terminalen Status erreicht. Zusätzlich wird eine im `complete.json` gemeldete `pullRequestNumber` jetzt auch bei unsauberem Ereignisabschluss als `PullRequestReference` registriert — unabhängig von `accepted.json`, einer scheiternden Abschluss-Mengenprüfung oder einer fehlenden Annahmemeldung —, pro Aufgabe dedupliziert.
- Die Anwendungslaufzeit ist jetzt .NET 11: App, Domain-Bibliothek, alle First-Party-Plugins sowie die CI-/Release-Toolchain wurden von `net10.0` auf `net11.0` gehoben — gebündelt mit der Paketlinie EF Core 11 / Microsoft.Extensions 11, SQLitePCLRaw 3.x und der xunit.v3-Testtoolchain; überflüssige, inzwischen von der Runtime bereitgestellte `Microsoft.Extensions.*`-Referenzen wurden entfernt.
- Neu angelegte Issues können jetzt automatisch aufbereitet werden (Issue-Aufbereitung, opt-in unter Einstellungen → Automatisierung → Issue-Aufbereitung über den globalen Schalter plus Repository-Auswahl): Nach einem einmaligen Beobachtungsbeginn, der den Bestand nie rückwirkend scannt, erzeugt ein neu angelegtes Issue genau einen internen Aufbereitungsauftrag — eine Zweck-markierte Aufgabe plus ein trigger-freies Ereignis, das in der SCM-Ereignisübersicht als „Issue-Aufbereitung" sichtbar und sofort fällig ist; selbst geschriebene Beschreibungsersetzungen lösen nichts erneut aus, und Trigger-Ereignisse auf demselben Issue laufen weiterhin auf die reguläre Aufgabe. Der Auftrag lässt einen festen Analyse-Prompt (Titel und Beschreibung — Verständlichkeit, Vollständigkeit, fehlende Angaben, offene Fragen, technische und fachliche Risiken, Zielkonflikte, Alternativen, mögliche Fehlinterpretationen) auf dem konfigurierten Aufbereitungs-Plugin laufen (mit derselben Fallback-Kette wie SCM-Ereignisse), zählt in die globale und Plugin-Ausführungsbegrenzung und ersetzt die Issue-Beschreibung anschließend remote über die Outbox — der Titel bleibt unverändert —; optional dokumentiert ein Issue-Kommentar Schwächen, offene Fragen, Ansätze, Risiken und Konflikte (Schalter `scm.issueaufbereitung.comment.enabled`, Standard an). Steht kein ausführbares Plugin bereit, startet nichts und der Auftrag wartet mit ehrlichem Grund; Fehler werden nur geloggt und im Aufgabenprotokoll vermerkt — das Issue bleibt unverändert und ein Fehlerkommentar wird nie erzeugt.
- Frei werdende Ausführungsplätze aus SCM-Ereignissen werden jetzt sofort nachgefüllt: Endet eine CLI-Ausführung oder wird eine Aufgabe pausiert beziehungsweise entpausiert, läuft sofort dieselbe priorisierte Startprüfung wie beim regulären Poll — wartende Ereignisse starten ohne Wartezeit auf den nächsten 60-Sekunden-Zyklus, weiterhin serialisiert über die bestehenden Aufgaben-Leases und atomaren Platz-Limits; der Poll bleibt als langsamere Sicherheitsnetz-Wiederholung bestehen.
- Parallele KI-CLI-Ausführungen aus SCM-Ereignissen sind jetzt begrenzbar: ein globales Limit (Einstellungen → Automatisierung → Aufgaben ausführen → „Maximale parallele Ausführungen") plus optional ein Limit je KI-Plugin (Einstellungen → Plugins → `<Plugin>` → „Ausführungsbegrenzung"), jeweils Ganzzahl ≥ 1 oder leer für unbegrenzt — das restriktivere der beiden gilt. Bei erreichtem Limit wartet das Ereignis mit ehrlichem Wartegrund und Protokolleintrag in der Queue und startet automatisch, sobald ein Platz frei wird; laufende Ausführungen werden nie unterbrochen, und Fortsetzungen aktiver Aufgaben werden vor fälligen Verzögerungen vor der Eingangsreihenfolge verteilt.
- Der SCM-Antwortkanal kann jetzt die Beschreibung eines Issues aktualisieren: Eine dauerhafte Outbox-Aktion mit deterministischer Aktions-ID schreibt den neuen Body per `PATCH` auf das Issue (der Titel bleibt unberührt), der markerbasierte Abgleich verhindert doppelte Schreibzugriffe auch über Neustarts hinweg, und Fehler sind typisiert (Authentifizierungs-/Berechtigungsfehler sperren ehrlich bis zum „Erneut prüfen", Ratenlimits und temporäre Fehler wiederholen automatisch mit Backoff).
- Über SCM-Ereignisse ausgelöste Ausführungen wählen ihr KI-Plugin jetzt robust: Eine gespeicherte Zuordnung (Aufgabe, Projekt- oder globaler Standard), die auf ein deaktiviertes, nicht installiertes oder nicht ladbares Plugin zeigt, wird zugunsten des nächsten konfigurierten Standards übersprungen; liefert keine Stufe ein ausführbares Plugin, bleibt das Ereignis mit verständlichem Wartegrund (mit Nennung der übersprungenen Zuordnungen) und Protokolleintrag in der Queue statt still verworfen oder dauerhaft gesperrt zu werden — nach Konfigurationskorrektur startet es automatisch, während eine ausdrückliche CLI-Wahl in der Ereignisübersicht weiterhin streng bleibt.
- Screenshot-Nachweise aus CLI-Läufen der SCM-Ereignisverarbeitung werden jetzt hostseitig veröffentlicht: Der Agent legt Nachweis-Bilder im über `attachmentsPath` bereitgestellten Verzeichnis des privaten Antwortkanals ab (ein eigener Upload ist nicht vorgesehen), die Anwendung prüft die Dateien (png, jpg, jpeg, gif, webp; je höchstens 10 MiB; höchstens 16 Dateien) und bettet sie als Anhänge eines GitHub-Kommentars ein — Dateien, die die Prüfung nicht bestehen, erscheinen im selben Kommentar einzeln mit Übersprungen-Grund; fehlgeschlagene oder ausstehende Veröffentlichungen bleiben als Integrationshinweis in der SCM-Ereignisübersicht sichtbar und lassen sich über „Erneut prüfen" wiederholen.
- Neue öffentliche Projektwebsite über GitHub Pages: Das Repository enthält jetzt eine statische Landing-Page (`site/`, deployed von `main` nach `https://martin-stromberg.github.io/Softwareschmiede/`), die die Anwendung präsentiert — Zweck, zentrale Features, Screenshots sowie Verweise auf Releases, Repository und Dokumentation — mit responsivem Hell-/Dunkel-Design angelehnt an die App-Themes.
- SCM-Aufgaben können eine verzögerte Ausführung anfordern: Steht im selben Text wie der Trigger das konfigurierbare Verzögerungs-Keyword (Standard `#verzögert`, Einstellungen → Automatisierung → Aufgaben ausführen) gefolgt von einer Angabe wie `30min`, `4h`, `2t`, `1w` oder `m1` (Kalendertag im Monat), ruht das Ereignis als „Verzögert" in der Queue — die Aufgabe wird bis zum Zielzeitpunkt pausiert, der Empfang wird auf GitHub kommentiert und der persistierte Timer übersteht Neustarts und blockiert den Auto-Shutdown (maximal 32 Tage).
- GitHub Enterprise: HTTPS-Git-Operationen authentifizieren jetzt auch gegen GitHub-Enterprise-Hosts — der `http.extraheader`-Key wird pro Operation an den Host der tatsächlich kontaktierten Remote-URL gebunden statt fest auf `github.com` verdrahtet; PR-Checkouts aus Forks binden das Fetch-Ziel an das Source-Repository des Forks.
- Die SCM-Ereignisüberwachung akzeptiert neben dem Repository-Owner jetzt auch das GitHub-Konto `github-actions` (`github-actions[bot]` / `app/github-actions`) als vertrauenswürdigen Autor/Bearbeiter — durch GitHub-Actions-Workflows angelegte Issues und Kommentare mit Trigger werden automatisch als Aufgaben ausgeführt.
- Sicherheit: Heruntergeladene Update-Pakete werden vor der Installation jetzt gegen den im Update-Manifest (`update.json`) veröffentlichten SHA-256-Hash geprüft — ein manipulierter oder beschädigter Download wird verworfen statt installiert. Der Update-Fortschrittsdialog zeigt dafür eine neue Phase „Verifikation".
- Sicherheit: Die GitHub- und Bitbucket-Plugins nutzen jetzt ausschließlich HTTPS als Git-Transport — die unsichere SSH-Konfiguration mit deaktivierter Host-Key-Prüfung (ein Man-in-the-Middle-Angriffsvektor) wurde entfernt. Bestehende verwaltete Arbeitskopien werden automatisch migriert: Beim nächsten Push, Pull oder PR-Checkout wird die Remote-URL auf HTTPS umgestellt und der vom Plugin geschriebene `core.sshCommand`-Eintrag entfernt.
