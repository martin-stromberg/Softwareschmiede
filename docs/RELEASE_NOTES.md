# Release Notes

## Important Notes Before Update

- There are no special notices.

## What's New

- New: the application can now be observed remotely through a self-hosted, read-only status page. A new, separately operated deployment unit `server/Softwareschmiede.StatusServer` (ASP.NET Core) accepts status snapshots from app instances over a token-authenticated SignalR hub (`/relay`), enriches them server-side with live GitHub data (open pull requests, releases, open issues) and renders them as a JavaScript-free HTML page (`/`, machine-readable `/status.json`) behind Basic Auth — the page is intentionally read-only in this version, with no remote command channel. On the app side, a new „Remote-Übersicht" section under Settings → Automatisierung enables the feature per installation: server URL, optional display name, a relay token stored in the Credential Store, an automatically generated persistent instance ID and an honest live connection status; once enabled, the app keeps an outbound-only `wss://` relay connection and pushes an initial plus periodic status snapshots (running tasks, pending user actions, recent SCM events, app version). The shared snapshot/handshake DTOs including a protocol version live in the new `src/Softwareschmiede.StatusContracts` project; server setup and operation (relay tokens, Basic Auth, systemd unit, nginx WebSocket upgrade) are documented in `server/README.md`.
- In separate-account monitoring mode, assigning the monitored account on an issue or pull request (notification reason `assign`) now triggers a task — the reference description becomes the job content without needing a mention or the trigger keyword, an empty description produces no task, and the assignment is only accepted when made by the repository owner, the separate account itself, or a trusted automation account (`github-actions[bot]` / `app/github-actions`); every assignment — including a re-assignment of an already linked reference — creates a new event that reuses and continues the existing task instead of duplicating it, and the delivered prompt explicitly states that it was triggered by an assignee assignment. The trigger applies only in `SeparateAccount` mode (the user-account mode keeps the trigger keyword as its only trigger), removing an assignment fires nothing, and no new configuration is required.

## Neuerungen

- Neu: Die Anwendung kann jetzt aus der Ferne über eine selbst gehostete, rein lesende Status-Webseite beobachtet werden. Eine neue, separat zu betreibende Deploy-Einheit `server/Softwareschmiede.StatusServer` (ASP.NET Core) nimmt Status-Snapshots der App-Instanzen über einen token-abgesicherten SignalR-Hub (`/relay`) entgegen, reichert sie serverseitig mit Live-GitHub-Daten an (offene Pull Requests, Releases, offene Issues) und rendert sie als JavaScript-freie HTML-Seite (`/`, maschinell `/status.json`) hinter Basic-Auth — die Seite ist in dieser Version bewusst rein lesend, ohne Kommando-Rückkanal. App-seitig aktiviert ein neuer Abschnitt „Remote-Übersicht" unter Einstellungen → Automatisierung die Funktion je Installation: Server-URL, optionaler Anzeigename, ein im Credential Store hinterlegtes Relay-Token, eine automatisch erzeugte persistente Instanz-ID und ein ehrlicher Live-Verbindungsstatus; bei aktiviertem Schalter hält die App eine ausschließlich ausgehende `wss://`-Relay-Verbindung und sendet initial sowie periodisch Status-Snapshots (laufende Aufgaben, wartende Anwenderaktionen, letzte SCM-Ereignisse, App-Version). Die gemeinsamen Snapshot-/Handshake-DTOs inklusive Protokollversion liegen im neuen Projekt `src/Softwareschmiede.StatusContracts`; Einrichtung und Betrieb des Servers (Relay-Tokens, Basic-Auth, systemd-Unit, nginx-WebSocket-Upgrade) sind in `server/README.md` dokumentiert.
- Im Überwachungsmodus „separates Konto" löst die Zuweisung des überwachten Kontos auf Issues und Pull Requests (Notification-Reason `assign`) jetzt eine Aufgabe aus — die Referenzbeschreibung wird ohne Erwähnung oder Trigger-Keyword zum Auftragsinhalt, eine leere Beschreibung erzeugt keine Aufgabe, und die Zuweisung wird nur akzeptiert, wenn sie vom Repository-Owner, vom separaten Konto selbst oder von einem vertrauenswürdigen Automatisierungskonto (`github-actions[bot]` / `app/github-actions`) stammt; jede Zuweisung — auch eine erneute Zuweisung einer bereits verknüpften Referenz — erzeugt ein neues Ereignis, das die bestehende Aufgabe wiederverwendet und weiterführt statt ein Duplikat anzulegen, und der zugestellte Prompt weist erkennbar darauf hin, dass er durch eine Assignee-Zuweisung ausgelöst wurde. Der Auslöser gilt nur im Modus `SeparateAccount` (der Benutzerkonto-Modus behält das Trigger-Keyword als einzigen Auslöser), das Entfernen einer Zuweisung löst nichts aus, und es ist keine neue Konfiguration erforderlich.
