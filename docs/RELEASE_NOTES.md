# Release Notes

## Important Notes Before Update

- Status server (breaking change): the configuration entries `Relay:Tokens`, `Relay:DevToken`, `Page:Username` and `Page:Password` have been removed without a migration path — relay tokens are now created and revoked in the admin UI (`/admin/tokens`, stored hashed in the SQLite database under `data/`), and page access runs through the cookie login of the new user management. After updating, open the status page once and register the first `Administration` account via `/register`, then issue new relay tokens under Tokens and update them in each app's Remote-Übersicht settings — previously configured relay tokens and the basic-auth credentials no longer work.

## What's New

- The execution limit no longer counts a task whose session sits idle at the verified input prompt against the parallelism limit merely because it still has an event in a non-final status: only events in an actual delivery/processing flight (`ZustellungVorbereitet`, `Zugestellt`, `InBearbeitung` — plus any unknown status, conservatively) hold the start slot, while accepted, deferred, waiting, and terminally unclarified events free it, since their delivery would go into the already-live session and needs no new start. As a side effect, events on structurally undeliverable tasks — removed, completed, archived, or missing a repository assignment — no longer stay `Wartend` forever but move to `VerarbeitungUngeklärt` with a descriptive reason, where the user can resolve or retry them after fixing the cause.
- New: the application can now be observed remotely through a self-hosted, read-only status page. A new, separately operated deployment unit `server/Softwareschmiede.StatusServer` (ASP.NET Core) accepts status snapshots from app instances over a token-authenticated SignalR hub (`/relay`), enriches them server-side with live GitHub data (open pull requests, releases, open issues) and renders them as a JavaScript-free HTML page (`/`, machine-readable `/status.json`) behind a cookie login with two permission levels — the page is intentionally read-only in this version, with no remote command channel. The status server carries a persistent user management (ASP.NET Core Identity + SQLite under `data/`): a first-run registration creates the `Administration` account, after which administrators manage users (create, switch the `Administration`/`Überwacher` level afterwards, deactivate, delete, reset lockouts — accounts lock automatically for one hour after three failed logins), relay tokens (created once-shown, hashed, revocable) and the session duration through an admin UI, while every user can change their own password in the profile. On the app side, a new „Remote-Übersicht" section under Settings → Automatisierung enables the feature per installation: server URL, optional display name, a relay token stored in the Credential Store, an automatically generated persistent instance ID and an honest live connection status; once enabled, the app keeps an outbound-only `wss://` relay connection and pushes an initial plus periodic status snapshots (running tasks, pending user actions, recent SCM events, app version). The shared snapshot/handshake DTOs including a protocol version live in the new `src/Softwareschmiede.StatusContracts` project; server setup and operation (user management, relay tokens, `data` directory, systemd unit, nginx WebSocket upgrade) are documented in `server/README.md`.
- In separate-account monitoring mode, assigning the monitored account on an issue or pull request (notification reason `assign`) now triggers a task — the reference description becomes the job content without needing a mention or the trigger keyword, an empty description produces no task, and the assignment is only accepted when made by the repository owner, the separate account itself, or a trusted automation account (`github-actions[bot]` / `app/github-actions`); every assignment — including a re-assignment of an already linked reference — creates a new event that reuses and continues the existing task instead of duplicating it, and the delivered prompt explicitly states that it was triggered by an assignee assignment. The trigger applies only in `SeparateAccount` mode (the user-account mode keeps the trigger keyword as its only trigger), removing an assignment fires nothing, and no new configuration is required.

## Wichtige Hinweise vor dem Update

- StatusServer (Breaking Change): Die Konfigurationseinträge `Relay:Tokens`, `Relay:DevToken`, `Page:Username` und `Page:Password` sind ersatzlos entfallen (kein Migrationspfad) — Relay-Tokens werden jetzt in der Admin-UI (`/admin/tokens`) erzeugt und widerrufen (gehasht in der SQLite-Datenbank unter `data/` gespeichert), der Seitenzugriff läuft über die Cookie-Anmeldung der neuen Benutzerverwaltung. Nach dem Update die Status-Seite einmal öffnen und über `/register` das erste `Administration`-Konto anlegen, danach unter Tokens neue Relay-Tokens erzeugen und in den App-Einstellungen (Remote-Übersicht) hinterlegen — bisherige Relay-Tokens und die Basic-Auth-Zugangsdaten funktionieren nicht mehr.

## Neuerungen

- Die Ausführungsbegrenzung zählt eine Aufgabe, deren Sitzung untätig am verifizierten Eingabeprompt steht, nicht mehr allein wegen eines Ereignisses in einem nicht-finalen Status als belegt: Nur Ereignisse in tatsächlicher Zustellung/Verarbeitung (`ZustellungVorbereitet`, `Zugestellt`, `InBearbeitung` — sowie konservativ jeder unbekannte Status) halten den Startplatz; aufgenommene, verzögerte, wartende und terminal klärbare Ereignisse geben ihn frei, da ihre Zustellung ohnehin in die lebende Sitzung läuft und keinen neuen Start benötigt. Folgeänderung: Ereignisse auf strukturell unzustellbaren Aufgaben — entfernt, beendet, archiviert oder ohne Repository-Zuordnung — bleiben nicht mehr dauerhaft `Wartend`, sondern wechseln mit sprechendem Grund in `VerarbeitungUngeklärt`, wo sie nach Korrektur der Ursache geklärt oder erneut geprüft werden können.
- Neu: Die Anwendung kann jetzt aus der Ferne über eine selbst gehostete, rein lesende Status-Webseite beobachtet werden. Eine neue, separat zu betreibende Deploy-Einheit `server/Softwareschmiede.StatusServer` (ASP.NET Core) nimmt Status-Snapshots der App-Instanzen über einen token-abgesicherten SignalR-Hub (`/relay`) entgegen, reichert sie serverseitig mit Live-GitHub-Daten an (offene Pull Requests, Releases, offene Issues) und rendert sie als JavaScript-freie HTML-Seite (`/`, maschinell `/status.json`) hinter einer Cookie-Anmeldung mit zwei Berechtigungsstufen — die Seite ist in dieser Version bewusst rein lesend, ohne Kommando-Rückkanal. Der StatusServer bringt eine persistente Benutzerverwaltung mit (ASP.NET Core Identity + SQLite unter `data/`): Eine Erst-Registrierung legt das `Administration`-Konto an, danach verwalten Administratoren über eine Admin-UI Benutzer (anlegen, Stufe `Administration`/`Überwacher` nachträglich ändern, deaktivieren, löschen, Sperrungen zurücksetzen — Konten sperren sich nach drei Fehlversuchen automatisch für eine Stunde), Relay-Tokens (einmalig angezeigt, gehasht gespeichert, widerrufbar) und die Sitzungsdauer; jedes Konto kann im Profil das eigene Passwort ändern. App-seitig aktiviert ein neuer Abschnitt „Remote-Übersicht" unter Einstellungen → Automatisierung die Funktion je Installation: Server-URL, optionaler Anzeigename, ein im Credential Store hinterlegtes Relay-Token, eine automatisch erzeugte persistente Instanz-ID und ein ehrlicher Live-Verbindungsstatus; bei aktiviertem Schalter hält die App eine ausschließlich ausgehende `wss://`-Relay-Verbindung und sendet initial sowie periodisch Status-Snapshots (laufende Aufgaben, wartende Anwenderaktionen, letzte SCM-Ereignisse, App-Version). Die gemeinsamen Snapshot-/Handshake-DTOs inklusive Protokollversion liegen im neuen Projekt `src/Softwareschmiede.StatusContracts`; Einrichtung und Betrieb des Servers (Benutzerverwaltung, Relay-Tokens, `data`-Verzeichnis, systemd-Unit, nginx-WebSocket-Upgrade) sind in `server/README.md` dokumentiert.
- Im Überwachungsmodus „separates Konto" löst die Zuweisung des überwachten Kontos auf Issues und Pull Requests (Notification-Reason `assign`) jetzt eine Aufgabe aus — die Referenzbeschreibung wird ohne Erwähnung oder Trigger-Keyword zum Auftragsinhalt, eine leere Beschreibung erzeugt keine Aufgabe, und die Zuweisung wird nur akzeptiert, wenn sie vom Repository-Owner, vom separaten Konto selbst oder von einem vertrauenswürdigen Automatisierungskonto (`github-actions[bot]` / `app/github-actions`) stammt; jede Zuweisung — auch eine erneute Zuweisung einer bereits verknüpften Referenz — erzeugt ein neues Ereignis, das die bestehende Aufgabe wiederverwendet und weiterführt statt ein Duplikat anzulegen, und der zugestellte Prompt weist erkennbar darauf hin, dass er durch eine Assignee-Zuweisung ausgelöst wurde. Der Auslöser gilt nur im Modus `SeparateAccount` (der Benutzerkonto-Modus behält das Trigger-Keyword als einzigen Auslöser), das Entfernen einer Zuweisung löst nichts aus, und es ist keine neue Konfiguration erforderlich.
