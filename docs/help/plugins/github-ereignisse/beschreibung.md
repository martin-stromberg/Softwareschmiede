# GitHub-Ereignisüberwachung — Beschreibung

## Zweck

Anfragen aus GitHub-Issues und Pull Requests können einer vorhandenen Aufgabe zugeordnet und an deren KI-CLI weitergegeben werden. So lässt sich die Arbeit an einer Aufgabe aus der Diskussion heraus anstoßen und in der Softwareschmiede nachverfolgen.

## Funktionsweise

Die Anwendung prüft regelmäßig Texte in GitHub-Issues und Pull Requests. Überwacht werden repository-weit alle offenen Issues und Pull Requests jedes aktivierten Projekt-Repositories; geschlossene Referenzen kommen hinzu, sobald sie seit der letzten Prüfung Aktivität zeigen. Dazu zählen Beschreibungen, Kommentare, Review-Kommentare und veröffentlichte Pull-Request-Reviews. Ein Text wird nur angenommen, wenn er das konfigurierte Trigger-Keyword (Standard `$Softwareschmiede`, einstellbar unter **Einstellungen → Automatisierung → Aufgaben ausführen**) enthält und sein Autor beziehungsweise bei einer Bearbeitung der Bearbeiter der angemeldete Repository-Owner ist. Die gesamte Überwachung lässt sich dort auch deaktivieren: Dann werden keine GitHub-Quellen abgefragt und keine Ereignisse automatisch zugestellt; bereits eingegangene Ereignisse bleiben erhalten und lassen sich weiterhin manuell öffnen, prüfen oder abbrechen.

Alternativ kann die Überwachung über die Auswahlbox **„Überwachungsmodus“** (Einstellungen → Automatisierung → Aufgaben ausführen) auf **„Separates Konto“** umgeschaltet werden. In diesem Modus arbeitet die Anwendung über ein eigenes GitHub-Konto (z. B. ein Bot-Konto), für das ein eigener Personal Access Token unter **Einstellungen → Plugins → GitHub → Authentifizierung** hinterlegt wird. Statt die Repositories zu durchsuchen, liest die Anwendung dann ausschließlich die GitHub-Benachrichtigungen dieses Kontos: Eine Aufgabe wird ausgelöst, sobald jemand das separate Konto frei stehend als `@Kontoname` in einer Issue- oder Pull-Request-Beschreibung oder einem Kommentar erwähnt — das Trigger-Keyword ist dafür nicht mehr nötig, der Autor muss aber weiterhin der Repository-Owner sein. Benachrichtigungen zu Repositories, die an keinem Projekt erfasst und aktiviert sind, werden ignoriert; die Anzahl der verworfenen Meldungen ist in den Integrationshinweisen der Ereignisübersicht einsehbar. Im separaten Modus entfällt die repository-weite Enumeration der Ereignisüberwachung; die Backmerge-Prüfung läuft davon unabhängig in einem eigenen Zyklus weiter.

Den Erwähnungsweg im separaten Modus kann auch eine im Repository hinterlegte Automatisierung nutzen: Zeitgesteuerte Abläufe legen dort regelmäßig Issues mit frei stehender Erwähnung des separaten Kontos an — etwa wiederkehrende Prüfaufträge zu Architektur, Abhängigkeiten oder Compliance. Solche Issues lösen Ereignisse genauso aus wie manuell geschriebene Erwähnungen; die Automatisierung legt dabei keinen neuen Prüfauftrag an, solange noch ein offenes Issue desselben Typs existiert.

Eingehende Texte erscheinen unter **SCM-Ereignisse**. Angenommene Kommentare und veröffentlichte Pull-Request-Reviews erhalten eine 👀-Reaktion; Beschreibungen nicht. Nach den Sicherheits- und Owner-Prüfungen wird die zugehörige Aufgabe automatisch gestartet — einschließlich der aus einem Ereignis neu angelegten Aufgaben: Die Anwendung klont das Repository, legt den Aufgaben-Branch an und startet die aufgelöste Standard-CLI (Aufgaben-, Projekt- oder globaler Standard). Wenn keine CLI zur Verarbeitung bereitsteht, bleibt der Eintrag dort sichtbar und GitHub erhält einen kurzen Wartehinweis. Die KI kann die passende Antwort im ursprünglichen Issue oder Pull Request selbst wählen.

Die CLI führt erlaubte Issue- und Pull-Request-Aktionen im Ereigniskontext **selbst** aus: Sie läuft im lokalen Klon des Repositories und erhält beim Start dieselbe SCM-Anbindung wie die Anwendung — bei GitHub als Prozessumgebung (`GH_TOKEN` für die `gh`-CLI, eine github.com-bezogene git-Anmeldung für Push/Fetch, deaktiviertes interaktives Credential-Prompt). Damit kann die KI z. B. Kommentare, Reviews, Labels, Merges inklusive Admin-Merge, Commits/Pushes oder das Schließen von Referenzen eigenständig über `gh` und git ausführen; die Anwendung muss dafür kein eigenes Aktionsmodell pflegen. Der Antwortkanal bleibt für Annahme, Status und Ergebnisrückmeldung bestehen: Vom Agenten selbst ausgeführte Remoteaktionen meldet er im Abschluss als kurzen Ergebnisbericht (`report`), vom Host auszuführende Antworten weiterhin als Kanalaktionen (`comment`, `reaction`, `pullRequest`), und nicht erlaubte oder unmögliche Aktionen dokumentiert er begründet über `noRemoteAction`. Einen selbst angelegten Pull Request meldet der Agent zusätzlich über die Nummer im Feld `pullRequestNumber`; die Anwendung verknüpft ihn mit der Aufgabe und überwacht ihn. Was der Agent tun darf, bleibt durch denselben Token und dieselben Repository-Berechtigungen begrenzt, die auch die Anwendung verwendet.

Betreibst du die Anwendung zweimal parallel — etwa eine Produktiv- und eine Vorabversion mit jeweils eigener Datenbank —, verhindert die Anwendung eine doppelte Bearbeitung derselben Anfrage: Hat das eigene Konto auf einen Kommentar bereits reagiert, gilt er als bereits bearbeitet und es entsteht kein neues Ereignis. Maßgeblich ist jede Reaktion des eigenen Kontos — die von der Anwendung vergebene 👀-Empfangsreaktion ebenso wie eine manuell gesetzte Reaktion (z. B. 👍). Voraussetzung ist, dass beide Installationen dasselbe GitHub-Konto verwenden; schreiben beide nahezu gleichzeitig, bevor eine von beiden reagiert hat, kann die Anfrage in Ausnahmefällen dennoch doppelt angenommen werden.

Eine optionale **Abschlussüberwachung** beendet Aufgaben automatisch: Die Auswahlbox **„Prüfmodus"** bestimmt, ob nur ereignisgesteuerte Aufgaben (mit mindestens einem SCM-Ereignis, Standard) oder alle Aufgaben beobachtet werden; Voraussetzung ist in jedem Fall eine SCM-Referenz — Aufgaben ohne verknüpftes Issue und ohne verknüpften Pull Request werden nie automatisch beendet. Sind alle verknüpften Pull Requests geschlossen/gemergt — oder ohne Pull Request das verknüpfte Issue geschlossen — wird die Aufgabe nach einer einstellbaren Wartezeit samt laufender KI-Ausführung auf „Beendet" gesetzt (Einstellungen → Automatisierung → Aufgaben beenden).

Bei der Zustellung kann die Anwendung konfigurierte Zusatztexte an den Prompt anhängen: Unter **Einstellungen → Automatisierung → Aufgaben ausführen** lassen sich je Ereignisart (Allgemein, Issue, Issue-Kommentar, Pull Request, Pull-Request-Kommentar inklusive Reviews) mehrzeilige Prompt-Anhänge hinterlegen — etwa Hinweise auf verfügbare Skills oder Bearbeitungsregeln, die nicht in jedem Kommentar wiederholt werden müssen. Ein leeres Feld hängt nichts an; die Trigger-Prüfung und der gespeicherte Ereignistext bleiben unverändert.

Zusätzlich kann die Anwendung **Backmerge-Pull-Requests automatisch mergen**: Ist bei einem Projekt-Repository ein vom Hauptbranch abweichender Basis-Branch konfiguriert, wird ein neu entdeckter Pull Request mit head = Hauptbranch (z. B. `main`) → base = Basisbranch als reine Arbeitsbranch-Aktualisierung erkannt und automatisch gemergt — eine inhaltliche Prüfung ist dafür nicht nötig. Die Prüfung läuft in einem eigenen Zyklus, unabhängig von der Ereignisüberwachung und immer unter dem Benutzerkonto — sie funktioniert daher auch bei deaktivierter Ereignisüberwachung und im Modus „Separates Konto". Gemergt wird nur, wenn GitHub den Pull Request als offen und mergebar meldet; geschlossene oder noch blockierte PRs werden im nächsten Prüfintervall erneut bewertet. Ist der Pull Request noch als Entwurf markiert, wird er nur dann vor dem Merge automatisch als bereit für Review markiert, wenn die Option **„Draft-Pull-Requests vor dem Merge automatisch aktivieren"** eingeschaltet ist — sonst wartet der Merge, bis der Entwurf manuell aufgehoben wurde. Der Merge läuft zuerst regulär; scheitert er am Branch-Schutz (z. B. fehlende Statuschecks oder Reviews), wird er nur dann einmalig als Admin-Merge wiederholt, der den Branch-Schutz umgeht, wenn die Option **„Bei blockiertem Merge Admin-Merge erlauben"** eingeschaltet ist. Die Funktion wird über den Modus **„Backmerge-Pull-Requests"** unter **Einstellungen → Automatisierung → Prozessabläufe** gesteuert (Deaktiviert / Global aktiviert / Projektbezogen aktivierbar); im projektbezogenen Modus muss zusätzlich die Option **„Backmerge-Pull-Requests automatisch mergen"** in der Basis-Branch-Kachel der Projektdetailansicht eingeschaltet sein. Voraussetzung ist außerdem ein Token mit Schreibrecht auf dem Repository (für den Admin-Merge ein Token mit Admin-Recht).

Für die CLI-Verarbeitung unterstützt die Anwendung aktuell Codex CLI, Claude CLI und Devin CLI nur dann, wenn deren erkannte Version, Schreibberechtigungen und tatsächlicher Zugriff auf den privaten Antwortkanal geprüft werden können. Unterstützte Versionsbereiche sind derzeit Codex `v0.114.x` und Claude Code `v2.1.x` (jeweils gleiches Major.Minor, beliebiger Patch) sowie Devin CLI `v3000.x` (gleiches Major, beliebige Minor- und Patch-Version). Eine erkannte Version außerhalb des Bereichs wird im Wartegrund mit CLI-Name und Version benannt und kann ausdrücklich bestätigt werden; ein unbekanntes Promptformat bleibt gesperrt. Die Anwendung ändert diese Berechtigungen nicht. Bei Devin CLI wird ein unterstützter `--permission-mode` (`accept-edits`, `dangerous` oder `bypass`) sowie `--respect-workspace-trust false` empfohlen; weitere freie Startparameter lassen die Prüfung bewusst fehlschlagen. Der KI-Simulator funktioniert nur, wenn die Anwendung ihn eigens im SCM-Modus startet. GitHub Copilot CLI und andere Plugins können derzeit nicht für diese Ereigniszustellung verwendet werden; ein Plugin in der Auswahlliste bedeutet nicht automatisch, dass es diesen Kanal unterstützt.

## Beispiele

- Ein Repository-Owner kommentiert in einem mit einer Aufgabe verknüpften Issue: „$Softwareschmiede Bitte prüfe den Fehler beim Export.“ Die Anfrage erscheint bei **SCM-Ereignisse** und kann an die passende CLI gehen.
- Ein Owner ändert die Beschreibung eines verknüpften Pull Requests und ergänzt den Trigger. Die neue Textfassung wird als Anfrage aufgenommen.
- Ist keine geeignete CLI verfügbar, bleibt der Eintrag wartend. Nach Behebung des Grundes kann er in der Ereignisübersicht erneut geprüft oder geöffnet werden.

## Einschränkungen

- Derzeit überwacht nur das GitHub-SCM-Plugin Ereignisse. Andere SCM-Plugins erhalten dadurch keine Ereignisüberwachung.
- Es werden nur Repositories überwacht, die an einem Projekt erfasst und aktiviert sind. Trifft ein qualifizierter Text an einer Referenz ohne lokale Aufgabe ein, wird die passende Aufgabe automatisch angelegt (Projekt aus dem überwachten Repository, Titel und Auftragstext aus den Ereignisdaten samt Quellverweis) und das Ereignis regulär verarbeitet. Bei Pull Requests wird vor der Anlage geprüft, ob bereits eine laufende Aufgabe denselben Kontext hat — der PR liegt auf ihrem Aufgaben-Branch oder schließt ihr verknüpftes Issue (`Closes #N` u. a.) —; dann geht das Ereignis an diese Aufgabe, statt eine zweite anzulegen. Geschlossene Referenzen werden nur dann einbezogen, wenn sie innerhalb des laufenden Aktivitätsfensters geändert wurden.
- Ein Kommentar, auf den das eigene Konto bereits reagiert hat, wird nicht als Ereignis aufgenommen — auch ein späteres Bearbeiten dieses Kommentars löst kein neues Ereignis aus, weil die Reaktion am Kommentar und nicht an der Textfassung hängt. Für eine neue Anfrage ist ein neuer Kommentar zu schreiben. Beschreibungen sind von dieser Prüfung ausgenommen, da sie keine Empfangsreaktion erhalten.
- Polling sieht den bei einer Abfrage aktuellen Textstand. Zwischenzeitlich überschriebene oder gelöschte Textfassungen können nicht rekonstruiert werden.
- Die Ereignisverarbeitung erfordert eine gültige GitHub-Anmeldung und passende Repository-Berechtigungen. Auch mit Codex oder Claude CLI kann ein Eintrag wartend bleiben, wenn die erkannte Version außerhalb des unterstützten Bereichs liegt, das Promptformat unbekannt ist oder Berechtigungen beziehungsweise Zugriff auf den geprüften Antwortkanal nicht unterstützt werden.
