# GitHub-Ereignisüberwachung — Beschreibung

## Zweck

Anfragen aus GitHub-Issues und Pull Requests können einer vorhandenen Aufgabe zugeordnet und an deren KI-CLI weitergegeben werden. So lässt sich die Arbeit an einer Aufgabe aus der Diskussion heraus anstoßen und in der Softwareschmiede nachverfolgen.

## Funktionsweise

Die Anwendung prüft regelmäßig Texte in GitHub-Issues und Pull Requests. Überwacht werden repository-weit alle offenen Issues und Pull Requests jedes aktivierten Projekt-Repositories; geschlossene Referenzen kommen hinzu, sobald sie seit der letzten Prüfung Aktivität zeigen. Dazu zählen Beschreibungen, Kommentare, Review-Kommentare und veröffentlichte Pull-Request-Reviews. Ein Text wird nur angenommen, wenn er das konfigurierte Trigger-Keyword (Standard `$Softwareschmiede`, einstellbar unter **Einstellungen → Allgemein → SCM-Ereignisse**) enthält und sein Autor beziehungsweise bei einer Bearbeitung der Bearbeiter der angemeldete Repository-Owner ist. Die gesamte Überwachung lässt sich dort auch deaktivieren: Dann werden keine GitHub-Quellen abgefragt und keine Ereignisse automatisch zugestellt; bereits eingegangene Ereignisse bleiben erhalten und lassen sich weiterhin manuell öffnen, prüfen oder abbrechen.

Eingehende Texte erscheinen unter **SCM-Ereignisse**. Angenommene Kommentare und veröffentlichte Pull-Request-Reviews erhalten eine 👀-Reaktion; Beschreibungen nicht. Nach den Sicherheits- und Owner-Prüfungen wird die zugehörige Aufgabe automatisch gestartet — einschließlich der aus einem Ereignis neu angelegten Aufgaben: Die Anwendung klont das Repository, legt den Aufgaben-Branch an und startet die aufgelöste Standard-CLI (Aufgaben-, Projekt- oder globaler Standard). Wenn keine CLI zur Verarbeitung bereitsteht, bleibt der Eintrag dort sichtbar und GitHub erhält einen kurzen Wartehinweis. Die KI kann die passende Antwort im ursprünglichen Issue oder Pull Request selbst wählen.

Die CLI führt erlaubte Issue- und Pull-Request-Aktionen im Ereigniskontext **selbst** aus: Sie läuft im lokalen Klon des Repositories und erhält beim Start dieselbe SCM-Anbindung wie die Anwendung — bei GitHub als Prozessumgebung (`GH_TOKEN` für die `gh`-CLI, eine github.com-bezogene git-Anmeldung für Push/Fetch, deaktiviertes interaktives Credential-Prompt). Damit kann die KI z. B. Kommentare, Reviews, Labels, Merges inklusive Admin-Merge, Commits/Pushes oder das Schließen von Referenzen eigenständig über `gh` und git ausführen; die Anwendung muss dafür kein eigenes Aktionsmodell pflegen. Der Antwortkanal bleibt für Annahme, Status und Ergebnisrückmeldung bestehen: Vom Agenten selbst ausgeführte Remoteaktionen meldet er im Abschluss als kurzen Ergebnisbericht (`report`), vom Host auszuführende Antworten weiterhin als Kanalaktionen (`comment`, `reaction`, `pullRequest`), und nicht erlaubte oder unmögliche Aktionen dokumentiert er begründet über `noRemoteAction`. Einen selbst angelegten Pull Request meldet der Agent zusätzlich über die Nummer im Feld `pullRequestNumber`; die Anwendung verknüpft ihn mit der Aufgabe und überwacht ihn. Was der Agent tun darf, bleibt durch denselben Token und dieselben Repository-Berechtigungen begrenzt, die auch die Anwendung verwendet.

Eine optionale **Abschlussüberwachung** beendet ereignisgesteuerte Aufgaben automatisch: Ist der verknüpfte Pull Request geschlossen/gemergt — oder ohne Pull Request das verknüpfte Issue geschlossen — wird die Aufgabe nach einer einstellbaren Wartezeit samt laufender KI-Ausführung auf „Beendet" gesetzt (Einstellungen → Allgemein → SCM-Ereignisse).

Bei der Zustellung kann die Anwendung konfigurierte Zusatztexte an den Prompt anhängen: Unter **Einstellungen → Allgemein → SCM-Ereignisse** lassen sich je Ereignisart (Allgemein, Issue, Issue-Kommentar, Pull Request, Pull-Request-Kommentar inklusive Reviews) mehrzeilige Prompt-Anhänge hinterlegen — etwa Hinweise auf verfügbare Skills oder Bearbeitungsregeln, die nicht in jedem Kommentar wiederholt werden müssen. Ein leeres Feld hängt nichts an; die Trigger-Prüfung und der gespeicherte Ereignistext bleiben unverändert.

Zusätzlich kann die Anwendung **Backmerge-Pull-Requests automatisch bestätigen**: Ist bei einem Projekt-Repository ein vom Hauptbranch abweichender Basis-Branch konfiguriert, wird ein neu entdeckter Pull Request mit head = Hauptbranch (z. B. `main`) → base = Basisbranch als reine Arbeitsbranch-Aktualisierung erkannt und automatisch per Admin-Merge (`gh pr merge --admin --merge`) gemergt — eine inhaltliche Prüfung ist dafür nicht nötig. Gemergt wird nur, wenn GitHub den Pull Request als offen und mergebar meldet; bei Drafts, geschlossenen oder noch blockierten PRs wird abgewartet und im nächsten Prüfintervall erneut bewertet. Die Funktion wird über den Modus **„Backmerge-Pull-Requests"** unter **Einstellungen → Allgemein → SCM-Ereignisse** gesteuert (Deaktiviert / Global aktiviert / Projektbezogen aktivierbar); im projektbezogenen Modus muss zusätzlich die Option **„Backmerge-Pull-Requests automatisch mergen"** in der Basis-Branch-Kachel der Projektdetailansicht eingeschaltet sein. Voraussetzung ist außerdem ein Token mit Schreibrecht auf dem Repository.

Für die CLI-Verarbeitung unterstützt die Anwendung aktuell Codex CLI, Claude CLI und Devin CLI nur dann, wenn deren erkannte Version, Schreibberechtigungen und tatsächlicher Zugriff auf den privaten Antwortkanal geprüft werden können. Unterstützte Versionsbereiche sind derzeit Codex `v0.114.x`, Claude Code `v2.1.x` und Devin CLI `v3000.11.x` (jeweils gleiches Major.Minor, beliebiger Patch). Eine erkannte Version außerhalb des Bereichs wird im Wartegrund mit CLI-Name und Version benannt und kann ausdrücklich bestätigt werden; ein unbekanntes Promptformat bleibt gesperrt. Die Anwendung ändert diese Berechtigungen nicht. Bei Devin CLI wird ein unterstützter `--permission-mode` (`accept-edits`, `dangerous` oder `bypass`) sowie `--respect-workspace-trust false` empfohlen; weitere freie Startparameter lassen die Prüfung bewusst fehlschlagen. Der KI-Simulator funktioniert nur, wenn die Anwendung ihn eigens im SCM-Modus startet. GitHub Copilot CLI und andere Plugins können derzeit nicht für diese Ereigniszustellung verwendet werden; ein Plugin in der Auswahlliste bedeutet nicht automatisch, dass es diesen Kanal unterstützt.

## Beispiele

- Ein Repository-Owner kommentiert in einem mit einer Aufgabe verknüpften Issue: „$Softwareschmiede Bitte prüfe den Fehler beim Export.“ Die Anfrage erscheint bei **SCM-Ereignisse** und kann an die passende CLI gehen.
- Ein Owner ändert die Beschreibung eines verknüpften Pull Requests und ergänzt den Trigger. Die neue Textfassung wird als Anfrage aufgenommen.
- Ist keine geeignete CLI verfügbar, bleibt der Eintrag wartend. Nach Behebung des Grundes kann er in der Ereignisübersicht erneut geprüft oder geöffnet werden.

## Einschränkungen

- Derzeit überwacht nur das GitHub-SCM-Plugin Ereignisse. Andere SCM-Plugins erhalten dadurch keine Ereignisüberwachung.
- Es werden nur Repositories überwacht, die an einem Projekt erfasst und aktiviert sind. Trifft ein qualifizierter Text an einer Referenz ohne lokale Aufgabe ein, wird die passende Aufgabe automatisch angelegt (Projekt aus dem überwachten Repository, Titel und Auftragstext aus den Ereignisdaten samt Quellverweis) und das Ereignis regulär verarbeitet. Geschlossene Referenzen werden nur dann einbezogen, wenn sie innerhalb des laufenden Aktivitätsfensters geändert wurden.
- Polling sieht den bei einer Abfrage aktuellen Textstand. Zwischenzeitlich überschriebene oder gelöschte Textfassungen können nicht rekonstruiert werden.
- Die Ereignisverarbeitung erfordert eine gültige GitHub-Anmeldung und passende Repository-Berechtigungen. Auch mit Codex oder Claude CLI kann ein Eintrag wartend bleiben, wenn die erkannte Version außerhalb des unterstützten Bereichs liegt, das Promptformat unbekannt ist oder Berechtigungen beziehungsweise Zugriff auf den geprüften Antwortkanal nicht unterstützt werden.
